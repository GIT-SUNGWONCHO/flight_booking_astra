# 문서 갱신·인계 지침

## 1. 목적과 문서 원본

읽기 순서는 AGENTS → NOW → README → FACTS다. [README의 문서 역할표](../../../README.md)를 따르고, 한 정보를 여러 문서의 원본으로 관리하지 않는다.

| 변경된 정보 | 갱신 위치 |
|---|---|
| AI 작업 범위·권한·핵심 제약 | [AGENTS](../../../AGENTS.md) |
| 다음 목표·최근 결과·현재 문제·번호가 있는 과제 | [NOW](../../../NOW.md), 25줄 이내 |
| 아키텍처·구성 요소·동작·운영·장애·완료 기준 | [README](../../../README.md) |
| 관측 사실·근거·해석 한계 | [FACTS](../../../FACTS.md), 90줄 이내 |
| 사용자와 확정한 실행 일정 | [공통 설정](../../../config/test_calendar.json) 변경 후 CALENDAR 생성 |
| 별도 API 연구의 설계·단계별 완료 조건 | [API 개발 문서](../../../api_booking/README.md) |

CLAUDE·BACKLOG는 안내만 한다. `docs/archive/`는 과거 증거이며 현재 실행 지시가 아니다.

## 2. 실행 결과를 남길 때

부모 prepare_day.json에서 실제 자식 실행 ID를 찾고 manual_booking.json·calendar_observer.json·network.json·heartbeat를 읽는다. 읽기 점검은 `dev-shots/checks/`를 본다.

예매 도착 범위와 계측의 첫 응답·오류·누락·P 전이를 각각 기록한다. 실행 시각과 실제 부팅 여부를 적고, 과거 로그인·창 상태를 현재 상태로 보고하지 않는다. 실패 단계와 다음 조치는 NOW에 남긴다.

## 3. 갱신 원칙

- 문서는 한글, 식별자·명령·파일명은 원문으로 유지한다. 계정·토큰·결제 식별자 원문은 기록하지 않는다.
- 새 문서를 늘리기보다 위 원본에 반영한다. 긴 과거 자료는 보관하고 현재 상태 문서에 누적하지 않는다.
- 운영 명세·현재 구현·검증 범위를 구분한다. 새 세션 재현 시험을 하지 않았다면 했다고 쓰지 않는다.

## 4. 완료 전 확인과 사용자 보고

링크·명령 진입점·캘린더 생성본 일치·문서 간 권한 및 상태 충돌을 검사한다. 문서 전용 변경은 실사이트 주문 시험을 요구하지 않는다.

사용자에게 **어느 문서를 어떤 역할로 바꿨는지, 무엇을 확인했고 무엇이 미완료인지** 보고한다.
