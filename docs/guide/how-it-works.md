# 동작 원리

무엇을 왜 그 순서로 하는지를 적는다. 쓰는 법은 [실전](real-day.md), 근거가 된 실측은 [왜 이렇게 만들었나](why.md).

## 1. 한 줄로

**사람이 예매할 때 브라우저가 대한항공 서버에 보내는 세 요청(조회 → 운임 → 주문)을, 좌석이 열리는 순간에 맞춰
같은 브라우저 안에서 프로그램이 연달아 보낸다.** 화면을 대신 눌러 주는 방식으로는 개방 13.66초 뒤에도 17단계 중 둘째 단계였고
좌석은 이미 없었다(2026-09-12). 요청을 직접 보내면 개방 2~3초 뒤에 주문이 나간다. 좌석을 잡은 뒤의 동의·결제수단 선택은
화면을 눌러 진행하고, 결제는 사람이 한다.

## 2. 세 요청

대한항공 누리집에서 마일리지 좌석을 예매하면 브라우저가 이 순서로 서버를 부른다.

| 순서 | 요청 | 하는 일 | 걸린 시간(실측) |
|---|---|---|---|
| 1 | 조회 `awardAvailability` | 그 날짜에 어떤 편·등급에 좌석이 있는지 | 1.4~1.8초 |
| 2 | 운임 `fareInformation` | 고른 편·등급의 마일리지와 세금 | 1.35~1.5초 |
| 3 | 주문 `inputTravellers` | 승객 정보를 넣고 **좌석을 잡는다**(예약번호가 나온다) | 6~7초(거절은 3초) |

- 순서를 건너뛸 수 없다. 조회 없이 운임, 운임 없이 주문을 보내면 서버가 즉시 거절한다.
- 한 로그인(세션) 안에서 요청을 겹쳐 보낼 수 없다. 앞 응답이 오기 전에 다음을 보내면 거절된다.
- 그래서 **주문을 보내는 가장 이른 시각 = 조회를 보낸 시각 + 조회 응답 + 운임 응답**이다. 2026-09 의 엿새 동안
  개방 2.0~3.0초 뒤였다.
- 주문이 좌석을 잡는 시점이다. 결제는 그 뒤의 일이고 급하지 않다(보유 시간 안에만 하면 된다).

## 3. 연습 통과 — 요청의 모양을 미리 얻는다

프로그램은 요청을 지어내지 않는다. 사이트가 실제로 보내는 요청에는 그때그때 바뀌는 헤더와 승객 정보가 들어 있어서,
**그날 그 브라우저가 실제로 보낸 요청**을 본으로 삼아야 한다.

그래서 실전 20분 전에 **이미 열려 있는 다른 날짜(캡처 날짜)** 로 사이트를 승객 확인 화면까지 실제로 한 번 가 본다.
그 사이 브라우저가 보내는 조회·운임·주문 요청의 헤더와 본문을 메모리에 잡아 둔다.

- 이때 사이트가 보내는 **주문 요청은 네트워크에서 막는다.** 캡처 날짜의 좌석을 실제로 잡지 않기 위해서다.
  막았는지 세어 두고(`'blocked': 1, 'unblocked': 0`), 하나라도 새어 나갔으면 그 실행은 멈춘다.
- 잡아 둔 것은 그 프로세스의 메모리에만 있다. 파일로 쓰지 않는다. 그래서 준비와 발사가 한 프로세스다.
- 09:00 에는 본의 **날짜만 목표 날짜로 바꿔** 조회를 보내고, 그 응답에서 목표 편·등급의 번호를 골라 운임을 다시 짜고,
  주문 본문은 본을 그대로 쓴다(주문 본문에는 여정이 없다 — 여정은 앞선 운임 단계가 서버 쪽에 남긴다).

캡처 날짜에는 일반석이 남아 있어야 한다. 설정이 `"captureDate": "auto"` 면 프로그램이 달력의 날짜 칸을 읽어
목표보다 앞선 날 중 일반석이 있는 가장 가까운 날을 고른다.

## 4. 정각 맞추기

- **시계**: PC 시계는 믿지 않는다. 인터넷 시각 서버(time.windows.com, time.google.com)와 견줘 차이를 재고,
  발사 1분 전에 한 번 더 잰다. 집 PC 는 하루 사이 수백 ms 씩 움직였고, 2.5초 틀려 있던 날도 있었다.
- **선발사**: 조회를 개방 0.8초 **전**에 보낸다. 조회가 서버에서 처리되는 데 1.4초쯤 걸리므로, 0.8초 먼저 보내도
  응답은 개방 뒤의 좌석을 담아 온다(2026-09-22~25 나흘 모두 그랬다). 너무 이르면 "아직 안 열림"을 받는다 —
  그때는 응답을 받는 대로 다시 조회한다(정각+8초까지).
- **대기 중 점검**: 08:50 에 로그인이 살아 있는지, 화면 상태가 그대로인지 다시 본다. 어긋났으면 처음부터 다시 준비한다.

## 5. 대체 예매 — 프레스티지가 안 되면 일반석

프레스티지는 한두 석이라 못 잡는 날이 많다. 그때 일반석이라도 잡으려면 일반석 준비가 **미리** 끝나 있어야 한다
(거절을 본 뒤 조회부터 다시 하면 3초가 더 든다).

같은 계정으로 브라우저를 하나 더 띄운다. 그 실행은 3.5초 늦게 일반석의 조회와 운임까지 끝내 놓고, **주문 직전에**
1순위가 남긴 신호 파일을 본다.

| 1순위의 결과 | 대체 실행 |
|---|---|
| 좌석을 잡았다 | 주문하지 않는다 |
| 거절됐다(예약번호 없음) | **곧바로 주문한다** |
| 결과가 애매하다 · 신호가 없다 · 5초 안에 안 온다 | 주문하지 않는다 |

애매하면 주문하지 않는다. 좌석 둘을 잡아 하나를 버리는 쪽보다 하나도 못 잡는 쪽을 택했다.
3.5초 늦추는 것은 1순위의 조회·운임과 같은 순간에 서버를 두드리지 않기 위해서다.

## 6. 주문은 한 번만

같은 주문이 두 번 나가면 좌석이 둘 잡힌다(같은 계정으로 동시에 두 번 주문했더니 예약번호가 둘 나왔다, 2026-09-24).
그래서:

- 주문 요청은 실행당 한 번이다. 응답이 애매해도 다시 보내지 않는다.
- 보내기 직전에 그 자리의 기록 폴더에 **표시 파일**을 하나 만든다. 이미 있으면 보내지 않는다. 두 프로세스가 동시에
  만들려 해도 운영체제가 하나만 성공시킨다.
- 그 표시는 12시간 뒤 다음 실행이 스스로 치운다. 미결제 좌석은 한 시간 안에 풀리므로 어제의 표시가 오늘을 막을 이유가 없다.
- 12시간 안에 다시 주문하려면 사람이 `--again` 을 붙여 "그래도 보낸다"고 해야 한다.

## 7. 좌석을 잡은 뒤 — 화면에 넘기기

주문 응답(예약번호)을 받으면 그 주문을 브라우저 화면에 넘겨, 사람이 예매하던 그 화면에서 이어 가게 한다.
여기서부터는 화면을 실제로 누른다: 약관 동의 두 개 → 마일리지 적용 → 결제수단 선택 → [결제하기].

- 넘긴 화면이 **방금 잡은 그 주문**인지(예약번호·날짜·마일리지) 확인한 뒤에만 누른다.
- 결제창(카드사·네이버페이)이 뜨면 멈추고 알림음을 낸다. 그 창 안에서는 아무것도 누르지 않는다.
- 넘기기에 실패해도 주문은 이미 기록돼 있다. 다시 주문하지 않고, 사람이 예약 조회에서 결제한다.

## 8. 계측 — 따로 도는 관찰자

`observer` 를 켜면 별도 브라우저(9233)가 개방 1.8초 전부터 10초 뒤까지 0.15~0.3초 간격으로 조회만 보내
**좌석 수가 언제 몇 석이었는지** 적는다. 예매에는 쓰이지 않는다. "오늘 왜 못 잡았나"(좌석이 몇 석이었고 우리 주문보다 먼저 줄었나)를 나중에 따지는 자료다.
계측이 실패해도 예매는 계속한다.

## 9. 프로그램이 스스로 하는 복구

| 일어난 일 | 하는 일 |
|---|---|
| 연습 통과가 끝까지 못 감 · 요청을 못 잡음 · 준비 중 프로그램이 죽음(주문 기록 없음) | Chrome 을 다시 띄워 처음부터 준비(세 번까지, 08:52 까지) |
| 로그인 토큰 만료 임박 · 화면 상태 어긋남 | 로그인부터 다시 준비 |
| 조회가 "아직 안 열림" · 일시 오류 | 응답 받는 대로 다시 조회(정각+8초까지) |
| 어제의 주문 기록이 남아 있음 | 보관 폴더로 옮기고 진행 |
| 주문 응답이 애매함 · 주문 뒤 화면 넘기기 실패 | **다시 주문하지 않는다.** 기록을 남기고 사람에게 넘긴다 |

원칙은 하나다. **주문이 나가지 않은 것이 확실하면 스스로 다시 하고, 나갔을 수 있으면 멈춘다.**

## 10. 프로그램 구성

| 파일 | 역할 |
|---|---|
| `astra.py` · `astra.cmd` | 입구. 설정을 읽어 아래를 부른다 |
| `config/run.json` · `dev/astra_config.py` | 설정과 그 해석(실행 목록·인자) |
| `api_booking/api_day.py` | 한 실행의 처음부터 끝: Chrome 띄우기 → 로그인·달력 → 캡처 날짜 고르기 → `live_order` → 실패 시 재준비 |
| `api_booking/live_order.py` | 연습 통과 → 대기·점검 → 발사(조회·운임·주문) → 화면 넘기기 |
| `api_booking/site_drive.py` | 화면을 실제로 누르는 부분(연습 통과, 동의·결제수단) |
| `api_booking/transport.py` | 브라우저 안에서 요청을 잡고 다시 보내기 |
| `api_booking/permit.py` | "주문은 한 번" 표시 파일과 12시간 규칙 |
| `api_booking/capture_date.py` | 달력을 읽어 캡처 날짜 고르기 |
| `dev/setup.py` · `dev/astra_browsers.ps1` | 로그인·달력 준비, 전용 Chrome 띄우기 |
| `dev/award_observer.py` · `dev/observer_chain.py` | 계측 |

더 자세한 규칙은 [API 예매 명세](../spec/api-booking.md), [계측 명세](../spec/observer.md).
