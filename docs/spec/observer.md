# 계측기 명세

기준: 2026-09-19. 코드: `dev/calendar_observer.py`, `dev/award_observer.py`, `dev/observer_chain.py`, `dev/browser_timing.py`,
`ke_award/calendar_probe.js`. 포트 9233, 프로필 `.debug-profile2`, **본인 네이버 계정**. 예매와 실패를 분리한다
(계측 실패로 예매를 멈추지 않는다).

## 1. 현재 방식: 달력 P 계측

- 9233에서 정상 달력 요청 `calendarFareMatrix`를 한 번 포착하고, 같은 세션의 보조 탭에서 목표 날짜로 바꿔 반복 전송한다.
- 표본마다 송신·수신 시각과 **목표 날짜의 프레스티지(P) 표시 여부**를 남긴다.
  P = `fareFamilyList`의 `KEBONUSPR`과 같은 위치의 status가 SOLDOUT이 아님. **편별 재고·좌석 수가 아니다.**
- 달력 화면은 계측 중 다시 읽지 않고, 끝난 뒤 새 API/DOM과 대조한다.

| 설정(공통 `config/test_calendar.json` observer) | 값 (2026-09-19 사용자 결정) |
|---|---|
| 창 | 개방 **−3초 ~ +10초** (`preMs` 3000, `postMs` 10000) |
| 간격 | **300ms** (`gapMs`) |
| 동시 요청 | **4** (`maxInflight`, 가드 상한). 가드 허용 250~1000ms·동시 1~4 |
| 슬롯 대기 | 150ms (`maxStartDelayMs`), 늦은 슬롯을 몰아 보내지 않음 |

실측(9/19 콜드·실전): 달력 응답 1.5~3.1초(중앙 1.8초) → 동시 4 한도로 **실제 간격 약 0.45초**, 표본 28~29, 오류 0,
건너뜀 15~16. 0.3초를 지키려면 동시 6~7이 필요하며 가드 상향은 별도 결정이 필요하다.

## 2. 실행

- 체인: `api_day.py --observer`가 `dev/observer_chain.py`를 별도 프로세스로 띄운다 → Chrome 9233 기동 → `setup.py`로
  네이버 자동 로그인·달력 → `calendar_observer.py --day <오늘>`(리허설은 `--rehearsal --at HH:MM:SS --target <열린 날짜>`).
- 네이버 세션은 Chrome 재기동 뒤에도 자동 로그인으로 유지됐다(9/19). 세션이 끊기면 사용자가 9233에서 네이버 로그인을 다시 한다.
- 실전 설정은 공통 설정과 같아야 한다. 다른 간격·동시 수 비교는 `--rehearsal`에서만.

## 4. 한계

- 달력 P는 날짜 단위 상태라 **좌석 1석 감소가 보이지 않는다.** 우리 주문이 언제 좌석을 잡았는지 알 수 없다.
- 서버가 요청 처리 중 어느 시점에 재고를 읽는지 모르므로 전이 시각은 송신~수신 구간으로만 말한다.
- 같은 PC의 부하를 예매와 공유한다.

### 5.1 결과 파일의 시각 축 — 원시값과 요약값이 다르다 (2026-09-23 정정)

| 위치 | 값 | 보정 |
|---|---|---|
| `events[].sentAt` · `receivedAt` | **로컬 시계 epoch ms** | **안 돼 있다.** 쓰려면 직접 보정해야 한다 |
| `edge.*` · `seatChanges.*` 등 요약 | **보정된 개방 기준 상대 초** | 돼 있다 |

코드는 `open_local = openAt_epoch − offset` 를 만든 뒤 `rel(ms) = (ms − open_local)/1000` 로 요약한다
(`dev/award_observer.py:119-137, 250`). 즉 **요약 = `(원시 − openAt)/1000 + offset`** 이다.
`offset` 은 **T−60초 재측정 뒤의 최종값**(`clockFinal`)이다.
`clockFinal` 이 없는 실행(9/20)은 시작 오프셋 기준이므로 다른 축의 값과 바로 비교하면 안 된다.

### 5.2 요약 필드의 정확한 뜻 (2026-09-23 정정)

이전 판은 아래 세 가지를 사실과 다르게 적고 있었다. 코드에 맞춰 고친다.
(코드 수정은 하지 않았다 — 별도 작업으로 남긴다.)

- **`edge.firstOpenSent` 는 "목표 편이 처음 보인 때"가 아니다.**
  `state='open'` 에는 **항공편 목록이 빈 응답**(`target='no-flights'`, `flights=0`)도 들어간다
  (`award_observer.py:68`). 실제로 9/20~22 의 `firstOpenSent`(약 −1.798초)는 전부 **첫 빈 목록
  요청**이었다. 9/23 은 빈 목록 표본이 0건이라 우연히 목표 편 최초 등장과 같았다.
  → 개방 경계를 볼 때는 `events[]` 에서 `target='found'` 이고 `seat` 이 있는 표본을 직접 골라야 한다.
- **`seatChanges[].firstReceivedWithTo` 는 "감소 응답 중 최초 수신"이 아니다.**
  **송신순으로 첫 감소 표본의 수신 시각**이다. 응답 순서가 뒤집히면 둘이 다르다 —
  9/23 이 실제로 그랬다(요약 +3.953 vs 실제 최초 수신 +3.794, [9/23 §3.1](../results/2026-09-23.md)).
- **`seatChanges` 구간은 재고 변경 시각이 아니다.** 우리 조회의 송신·수신 시각일 뿐이며,
  서버가 요청 처리 중 언제 재고를 읽는지는 모른다. 단조 감소를 가정할 때의 **보수적 가능 구간은
  `lastSentWithFrom` ~ (감소 응답 최초 수신)** 이다.

요약: `edge`(마지막 미개방 송신, 첫 열림 송신], `seatChanges`(N석 마지막 송신 ~ N−1석 첫 수신).
- 체인: `observer_chain.py`가 `awardObserver.mode`(`both` 기본)에 따라 예매 조회 계측기 준비(캡처·달력 복귀·7초 안정) 뒤
  달력 계측기를 띄운다. 달력 계측기 준비 실패는 개방 3분 전까지 1회 재시도.
- **동기 Playwright 연결 중 `time.sleep` 금지**: 잠든 클라이언트가 CDP 메시지를 처리하지 않아 같은 Chrome의 새 문서·다른
  클라이언트 연결이 멈춘다(9/19 리허설에서 달력 계측기 시간 초과·화면 로딩 멈춤). 대기는 `page.wait_for_timeout`.
- 리허설(9/19 22:25·22:40·22:54, 이미 열린 2027-09-09): 표본 47~48, 송신 지연 최대 4ms, 응답 약 7KB·1.6초,
  `ERT.3002` 2~3건(성긴 구간, 의미 미확인). 달력 계측기와 함께 실행 통과(22:54).
- 리허설 전용 `--family KEBONUSEY`로 좌석 있는 등급 읽기 확인(9/20: 일반석 `9` 87/87). 오류 응답은 코드와 정제 메시지만 남긴다
  (`ERT.3002` = 일시 처리 실패 문구).
- 본 예매 영향(9232 조회→운임 반복, 켬 14회·끔 9회): 조회 중앙 1,676 vs 1,629ms, 운임 1,477 vs 1,424ms.
  차이 약 +50ms로 표본 편차(±130ms) 안. 촘촘한 구간에서 1,928ms 1회 — 영향 가능성은 09시 실측으로 계속 본다.

### 5.3 동시 상한에 걸리면 발사가 생략된다

`maxInflight` 12 를 넘으면 그 슬롯은 `{"kind": "skipped", "why": "inflight"}` 로 기록되고 **보내지 않는다.**
9/20~22 는 생략 0회였으나 **9/23 은 예정 66회 중 9회가 생략됐다**(id 12~18, 31, 37 — 응답 57회).
응답이 느려지면(그날 최초 요청은 2.801초) 상한에 걸리므로, **표본 수는 응답 시간에 따라 달라진다.**
결과를 읽을 때 `slots` 와 `responses` 를 함께 본다.
