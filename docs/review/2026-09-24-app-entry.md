## 1. 왜 하나

질문은 하나다 — **경쟁자는 우리 웹 경로의 바닥보다 어떻게 빠른가.**

- **웹 경로의 바닥은 주문 송신 약 +1.9초다.** 조회 응답은 일찍 보내도 빨리 오지 않는다
  (9/23: −1.797초 송신 조회가 +1.004초 완료, −0.8초 송신 우리 조회는 +0.599초 완료, 개방 전 응답 다수가
  +0.937초 부근에 몰림). 조회 없이 운임, 운임 없이 주문은 불가하다([FACTS §1](../../FACTS.md)).
  +0.6초 부근 조회 완료 + 운임 약 1.36초 → 우리 9/23 +1.990초가 이미 그 자리다.
- **9/21 이 가장 강한 근거다.** 2석이 두 번 줄었다. 두 번째 감소는 우리 주문으로 추정된다(우리 주문 송신
  +2.408 → 그 경계까지 +1.346~1.494초로, 같은 날 오후 통제 실험 Δ 1.36~1.51초와 겹치고 주문도 성공).
  즉 **09시 부하에서도 웹 주문의 Δ는 평소와 같았다.** 첫 번째 감소는 송신 축에서 우리 흔적보다 약 1.5초 앞이다.
  같은 웹 주문(같은 Δ)이었다면 +0.9초 부근 송신이어야 하는데, 이는 웹 바닥보다 1초 빠르다.
  [9/21](../results/2026-09-21.md) · [9/23 §4](../results/2026-09-23.md) · [검토 대조](2026-09-23-audit.md)
- 이 추론은 **[조건부]**다(Δ가 그 주체에게도 같다는 가정, 9/21 표본 1). 그러나 가정이 틀렸다면 그 자체가
  "경쟁자의 주문은 우리 웹 주문과 다르게 처리된다"는 뜻이라 결론 방향은 같다.

## 3. 조사 2 — 아이폰 앱 트래픽 (mitmproxy)

**역할**: 로컬 세션은 mitmproxy 실행과 결과 요약까지. **아이폰 조작은 사용자가 직접** 한다.

PC(로컬 세션):
```powershell
.venv\Scripts\python.exe -m pip install mitmproxy
.venv\Scripts\mitmdump.exe -s dev\app_trace.py
```
(설치 위치가 다르면 `mitmdump -s dev\app_trace.py`. PC IP 는 `ipconfig` 의 Wi-Fi IPv4. 방화벽이 8080 을 막으면 허용.)

아이폰(사용자):
1. PC 와 같은 Wi-Fi → Wi-Fi (i) → 프록시 구성 **수동** → `PC IP` / `8080`.
2. Safari 로 `mitm.it` → iOS 프로필 받기 → 설정 > 일반 > VPN 및 기기 관리에서 설치.
3. 설정 > 일반 > 정보 > **인증서 신뢰 설정**에서 mitmproxy 켜기.
4. 대한항공 앱: 로그인 → **이미 열린 날짜** 마일리지 조회 → 등급·운임 선택 → **승객 화면까지만.**
5. 끝나면 PC 에서 Ctrl+C → **아이폰 프록시 끄기, 프로필 삭제.**

- **안전**: 예약 생성 계열 POST/PUT/PATCH(traveller/order/reserv/pnr/hold/purchase/ticket)는 **프록시가 403 으로
  막는다.** 본문·헤더·쿠키·토큰은 저장하지 않는다(호스트·경로(쿼리 제외)·메서드·상태·크기·시각만).
- **결과**: `dev-shots/research/app-trace-<시각>.jsonl`, `.summary.json`
  (`hosts` 호출 수, `writes` 쓰기 경로, `blocked` 차단, `tlsFailedHosts` 인증서 고정 추정).

| 관찰 | 뜻 |
|---|---|
| 앱이 `www.koreanair.com` 의 같은 경로(`awardAvailability` → `fareInformation` → `inputTravellers`)를 쓴다 | 앱은 더 빠른 입구가 아니다 → 앱 가설을 닫는다 |
| 다른 호스트·다른 경로를 쓰거나 **단계 수가 다르다**(예: 운임 없이 주문, 좌석 선점 호출) | 유력 후보 → 그 경로의 응답 시간 측정 설계로 |
| 앱이 네트워크 오류(`tlsFailedHosts` 에 기록) | 인증서 고정. 내용은 못 보지만 **접속 호스트 이름**은 남는다 → 조사 1 과 대조. 더 보려면 Mac + USB `rvictl -s <UDID>` + Wireshark 로 SNI·시각만 캡처 |

### 7.3 판단

- **트리 B(대기열이 우리를 붙잡았다 푼다 → 웹 바닥의 정체)는 약해졌다.**
  "개방 시각에 공통으로 붙잡힘"은 5일 중 1일, 그것도 계측 세션에서만 보였고 예매 세션에는 없었다.
  웹 바닥의 큰 몫인 조회 약 1.4~1.7초는 개방 전후와 관계없는 **평소 처리 시간**으로 보인다 [추정].
- **배제하지는 못한다.** Queue-it 는 보너스 예매에 실제로 설정돼 있다(7.1). 응답 헤더를 남기지 않았으므로
  Queue-it 가 응답에 보냈을 수 있는 신호(대기 지시 헤더 등)는 볼 수 없었다.
  9/23 계측 세션의 붙잡힘이 Queue-it 때문인지, 같은 세션의 동시 요청 처리 때문인지도 판단 불가다 [가설 둘 다].
- 한 줄 결론: **B 는 약해짐(웹 바닥을 설명하지 못함). 단, 응답 헤더가 없어 대기열 관여 자체는 판단 불가.**

### 7.4 제안 — 다음 09시 계측에서 남길 것 (설계만, 코드 미변경)

계측·예매 코드 반영은 사용자가 실전 세션과 정한다. 새 요청을 늘리지 않고 **기존 계측 조회의 응답**에서만 남긴다.

- 조회 응답마다: **응답 헤더 이름 목록**(값 없이), 그리고 이름이 `x-queueit-` 로 시작하는 헤더의
  **존재 여부와 길이**(값은 대기열 토큰일 수 있으므로 저장하지 않음. 값이 고정 열거형으로 확인되면 그때 다시 정한다).
- `response.redirected`·`response.url` 의 **호스트만**(대기열 호스트로 넘어갔는지), `Retry-After` 존재 여부.
- 세션 비교: 같은 날 예매 세션(9232) 조회에도 같은 항목을 남겨 7.2 의 "계측 세션만 붙잡힘"이 되풀이되는지 본다.
- 저장하지 않는 것: `Set-Cookie` 값, 쿠키, `QueueITAccepted` 값, 인증 토큰, 대기열 토큰, 응답 본문.
- 판독: 9/23 과 같은 몰림이 다시 나올 때 `x-queueit-*` 가 함께 나오면 대기열 관여, 아니면 세션 처리 쪽으로 좁힌다.
