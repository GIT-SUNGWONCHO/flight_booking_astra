# 2026-09-19 집 PC 이관 인계

이 문서는 클라우드 세션이 집 PC 로컬 세션에 넘기는 인계본이다. 집 PC가 앞으로
리허설·실전테스트·중요목표를 모두 수행하는 실행 PC다. 여기 적힌 계획은 사용자
승인을 받은 것이며, 승인 범위를 넘는 확대 해석을 하지 않는다.

## 1. 지금 상황

- 저장소 최신 커밋은 9/14 `28069ba`다. 그 뒤 GitHub에 올라온 것이 없다.
- 9/16 회사 PC에서 ICN→CDG 실전테스트를 1회 더 했고, 9/18 오전까지 개발이
  이어졌다. **그 코드와 증거는 GitHub에 올라오지 않았고 복구할 수 없다.**
  9/14 커밋을 기준으로 다시 만든다.
- 주말 동안 회사 PC에 접속할 수 없다. 집 PC(Windows, Chrome 설치됨)에서
  개발·리허설·실전을 모두 한다.

## 2. 9/16 실전 결과와 해석 한계

사용자 구두 보고(원본 증거 없음, 값은 로컬 시계 기준):

- 주문 전송 약 3.2초, 주문 **실패**. 실패 사유 코드는 확인 불가.
- 계측 3.4초 송신분 응답은 **좌석 있음**, 4.3초 송신분 응답은 **매진**(수신 6초).

여기서 모순이 있다. 주문(3.2초)이 "좌석 있음"을 받은 계측(3.4초)보다 먼저
도착했는데 실패했다. "3.2~4.3초 사이 매진"만으로는 설명되지 않는다. 가설 셋을
모두 열어 둔다. **어느 것이냐에 따라 시간단축이 정답인지 자체가 갈린다.**

1. **달력 P는 주문 재고가 아니다.** FACTS에 이미 "calendarFareMatrix의 P는
   목표 날짜의 KEBONUSPR 인덱스 status 조건이지 편명별 재고·서버 보유 시각이
   아니다"라고 적혀 있다. 계측기가 본 값과 주문이 소비하려던 재고가 다를 수 있다.
2. **주문은 서버 안에서 재고 확인까지 더 걸린다.** 도착이 빨라도 처리 순서가 늦다.
3. **큐잉.** FACTS에 `x-queueit-ajaxpageurl` 헤더 관측 기록이 있다. 대기열이
   있으면 전송 속도보다 대기열 위치가 결정적이다.

가설 1은 "주문으로 좌석 1석을 실제로 줄이고 계측기가 그 전이를 보는지" 확인하면
판별된다. 사용자가 제안한 실험이며 09시 이후 계측 고도화 단계에서 수행한다.

## 3. 코드에서 확인한 것 — 계획의 근거

### 3.1 `api_booking/live_order.py`에 시계 보정이 없다

발사 시각을 `datetime.now(KST)` 로컬 시계 그대로 쓴다. `measure_clock()`을
부르지 않는다. UI 예매 경로(`dev/autorun.py`)는 NTP 오프셋을 반영하는데 **API
경로만 빠져 있다.** `ke_award/clock.py` 주석대로 Windows 로컬 시계는 수 초까지
틀어질 수 있다. 따라서 9/16의 "3.2초"도 보정되지 않은 값이며, 매진 시각 추정이
그만큼 흔들린다. 선발사보다 먼저 고쳐야 한다.

### 3.2 정각 전 발사를 코드가 일부러 막고 있다

`live_order.py` 발사 대기 루프에 그대로 있다.

    # 정각 전에 쏘지 않는다. 미개방 응답이면 재시도 없이 끝나기 때문이다.
    if left <= 0:
        break

그리고 `availability.py`는 `ERT.10032`를 `not-open`으로 판정하고 주문 0회로
끝낸다. 재시도 경로가 없다. **그래서 선발사는 단독으로 성립하지 않는다.**
미개방 응답 시 즉시 재조회하는 경로가 반드시 같이 들어가야 하며, 없으면 당긴
만큼 한 발을 그대로 날린다.

### 3.3 로그인 자동화는 이미 있다

`dev/setup.py`(848줄)에 `login_idpw()`(스카이패스 ID/PW, 아이디/스카이패스번호
탭 두 개 처리), `login_naver()`, `KE_LOGIN_MODE` 분기, 포트별 로그인 방식 표시,
로그아웃 상태 감지 후 재로그인이 모두 있다. 무인 체인은 새로 만드는 것이
아니라 기동→로그인→준비→발사를 잇는 작업이다.

### 3.4 KRW 준비가 API 경로에 연결되어 있지 않다

`prepare_krw()`는 `dev/autorun.py`와 `dev/prepare_day.py`에만 붙어 있고
`api_booking/live_order.py`에는 없다. CDG·FCO 출발은 USD로 표시될 위험이
실제로 있는데 API 경로에 대비가 없다. 연결해야 한다.

### 3.5 계측 간격은 설정만으로 4배 조밀해진다

`ke_award/calendar_probe.js`의 가드가 `gap 250~1000ms`, `maxInflight 1~4`를
허용한다. 현재 설정은 1000ms·2다. 250ms·4까지는 코드 변경 없이 설정만 바꾸면
된다. 그 아래는 "시험되지 않은 구간"이라 일부러 막은 것이므로 리허설 근거 없이
뚫지 않는다.

## 4. 확정 계획

| 단계 | 내용 |
|---|---|
| P0 | 집 PC 환경 구축 + 자동 로그인 스모크 테스트 |
| P0.5 | AGENTS.md 무인발사 조항 개정 |
| P1 | 시계 보정 + 미개방 재시도 + 선발사 (3종 세트, 분리 금지) |
| P2 | 무인 체인(기동→로그인→준비→발사) + KRW 연결 + 08:20 예약 실행 |
| P3 | 콜드 스타트 리허설 (로그아웃·Chrome 종료 상태에서 시작) |
| P4 | 09:00 실전테스트 + 계측기 기존 설정으로 병행 |
| P5 | 09시 이후: 계측 고도화, 주문 오류 상세 수집, 문서 일괄 정리 |

시간이 모자라면 P2를 버리고 사용자가 09:00에 수동 무장한다. **선발사는 끝까지
지킨다.** P0에서 로그인이 막히면 09:00을 취소하고 9/20 FCO→ICN으로 재편성한다.

### P1 상세

- **시계 보정**: `live_order.py`에 `measure_clock()` 연결. 보정 실패 시
  **선발사 금지**. 오프셋·불확실성을 증거에 기록.
- **미개방 재시도**: `not-open` 응답 시 즉시 재조회. 횟수·간격 상한은 파라미터.
- **선발사**: `--pre-fire-ms N`. 기본값 0(현행과 동일). 리허설에서 측정한
  편도지연으로만 값을 올린다. 미검증 값을 실전에 넣지 않는다.

### P3 리허설 조건 (사용자 지정)

로그아웃 상태 + 기존 Chrome 창 전부 닫힌 상태에서 시작한다. 실전 09시에
그대로 재현되는 조건이어야 한다. CDG→ICN 이미 열린 9월 날짜, 프레스티지 1석으로
실제 주문 1건까지 진행하고 **결제창에서 정지한다.**

## 5. 승인된 정책 변경

사용자가 명시 승인했다. AGENTS.md에 이 범위로 반영한다.

- **무인 발사·주문 허용**: 리허설과 실전테스트에서 프로그램이 무장·발사하고
  주문 1건까지 진행할 수 있다.
- **최종 결제는 여전히 사용자만 한다.** 결제창 안에서는 누르지 않는다.
- 저장 허용 항목에 **주문 오류 코드·메시지**를 추가한다. 식별자 원문·토큰·
  쿠키·pageTicket은 여전히 저장하지 않는다.

## 6. 계정 분리 (사용자 확정)

- **API 예매 9232: 와이프 스카이패스 계정.** `.env`의 `KE_SKYPASS_ID`/`KE_SKYPASS_PW`,
  `KE_LOGIN_MODE=skypass`. `KE_LOGIN_TAB`은 비워 둔다(숫자면 자동으로 스카이패스 탭).
- **계측 9233: 본인 네이버 계정.** 네이버가 캡차·2단계 인증으로 막히면 차순위로
  와이프 계정을 같이 쓴다. 계정을 같이 쓰면 느려질 수 있어 분리하는 것이 기본이다.
- 실전테스트와 중요목표 모두 같은 규칙을 쓴다.
- 비밀번호는 `.env`에만 둔다. 대화창·문서·터미널 출력에 옮기지 않는다.
