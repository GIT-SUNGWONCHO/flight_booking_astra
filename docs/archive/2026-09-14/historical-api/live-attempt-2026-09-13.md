## 3. 실측으로 확인된 사실

### 3.1 전송 경로와 헤더

- 수집기는 개인정보 보호로 **헤더를 기록하지 않고 요청 본문 필드도 상당수 가린다**. 그래서 요청을 재구성해 보내는 방식은 불가능했다.
- 대신 `window.fetch`/`XMLHttpRequest`를 감싸 사이트가 보내는 요청을 **메모리에서** 가로채 재전송했다. 헤더 이름: `Accept`, `Content-Type`, `channel`, `ksessionId`, `timestamp`, `x-dtpc`(운임·주문), `x-queueit-ajaxpageurl`. 값은 기록하지 않았다(`ksessionId`는 인증 토큰).
- **Playwright `add_init_script`로 건 후킹은 연결이 끊기면 사라진다.** 캡처는 페이지 문서의 `window.__KE_TX`에 있어 페이지 이동·새로고침 시 사라진다. 제어 프로세스를 내리면 안 된다.
- 합성 이벤트(`dispatchEvent`)는 `kds-*` 커스텀 엘리먼트에서 동작하지 않아 좌표 기반 실제 마우스 클릭을 쓴다.

### 3.2 요청·응답 계약(수집 `20260912-232135-f66cf6b8`, 30행·오류0·비200 0)

- `awardAvailability` 요청: `currency`, `segmentList[{departureDate, departureAirport, arrivalAirport}]`, `travelers`, 가려진 최상위 3개. **등급 필드가 없다.** 응답 `upsellBoundAvailList[].availFlightList[]`에 `flightId`, `flightInfoList[{flightNumber, operationCarrierCode, departureDateTime, codeShare}]`, `commercialFareFamilyList[{recommendId, fareFamily, seatCount, soldout}]`가 있고 EY·PR·FC가 함께 온다.
- `fareInformation` 요청: `recommendList[{recommendId, flightId}]`, `currency`(54B). 응답: `pnrFareInfo{currency, amount, totalAmount, mileage}`, `boundList[].segmentList[]{flightNumber, fareFamily, cabinClass, departureDateTime}`, `pageTicket`, `jsessionId`.
- `inputTravellers` 요청: `travellerInfoList[{travellerId, +10}]`, **`contactList` 2개**, `preferLanguage`. **여정·날짜·등급·운임이 없다**(가려진 최상위 0개). 서버 세션 상태를 따르므로 `fareInformation` 뒤에 순서대로 보내야 한다. 응답: `pnr`, `availableOnHold`, `boundList`, `createDateTime`, `createDateTimeOfKST`, `officeId`, `pnrFareInfo`, `reservationContactList`. **`pnrFareInfo`는 앞선 수집에서는 없었다.**
- A4b 모델은 `contactList` 1개만 허용해 실제 요청을 통과시키지 못한다(미수정).

## 4. 사용자가 확인해 준 사실

- **동의를 거친 pnr은 좌석을 임시로 보유한다.** 예약 조회에 반영되지 않고 일정 시간이 지나면 좌석을 다시 내놓는다. **결제를 완료해야 예약이 된다.** (보유 지속 시간은 미관측)
- 9/10 수집에서 만든 미결제 주문은 예약 조회에 남아 있지 않았다.
- 우선순위: **1순위 T0→pnr 단축, 2순위 결제창.** 좌석확보까지 6~7초도 의미가 있다.
- 기존 브라우저 매크로는 09시에 성공한 적이 없어(9/11·9/12 모두 2/17단계 매진) 일반 예매 테스트는 중단하고 API 예매에 집중한다.
- 계측기 관측상 프레스티지는 5~6초대에 매진으로 보였다.
- 결제는 네이버페이가 맞다.
- **동의부터는 API가 아니라 기존 예매 절차(브라우저 클릭)를 따른다.**
- 실전은 **처음 세션의 날짜 선택부터** 브라우저가 따라와야 한다.

## 6. 실패·차단 원인

1. **브라우저 연계 미구현.** 현재 구조는 캡처하려고 브라우저를 한 번 통과시킨 뒤 결제 게이트에 멈춰 두고, API가 화면과 무관하게 주문한 다음 게이트를 다시 열어 새 주문이 떠 있기를 기대한다. 사용자 요구(달력에서 시작 → 결제 브라우저까지 동행)와 다르다.
2. **캡처 날짜·등급 ≠ 발사 날짜·등급 조합을 한 번도 시험하지 않았다.** 모든 리허설이 09-07 일반석 동일 조건이었다.
3. **결제 단계 자동화가 명세를 따르지 않았다.** 기존 `steps.json` 17단계를 통째로 쓰지 않고 일부만 옮겨 모달 완료 판정·하단 고정 버튼·결제수단 선택이 차례로 누락됐다.
4. 시간 압박 속에 **확인되지 않은 기대를 완료로 보고**했다(§8).
