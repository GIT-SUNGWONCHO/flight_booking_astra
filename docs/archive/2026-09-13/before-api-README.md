## 1. 목표·현재 구현·측정 기준

‘개방’은09:00에 새 여행 날짜의 예매가 가능해지는 시점이다. 개발과 일반석 리허설은 이미 열린 날짜로 진행한다. 로그인·KRW·승객·연락처의 준비 완료를 전제로 하며 초안 작성 기능을 다시 개발하지 않는다.

좌석 1개가 풀렸고 약6초 후 관측에서 없었다는 사용자 설명만으로 경쟁자의 결제 완료 시각·API 사용·정확한 좌석 보유 시점을 알 수 없다. 예약번호 생성, 좌석 보유, 결제, 발권은 각각 별도 상태다. 같은 날짜라도 캐시·다른 사용자의 행동으로 재고 관측과 우리 주문의 인과가 일치하지 않을 수 있다.

| 지표 | 시작 → 종료 | 판정 기준·현재 한계 |
|---|---|---|
| **성능 목표** | 개방 기준T0 → 서버의 해당 구간·등급 좌석 보유 | 현재 직접 확인 불가. 검증된 서버 상태·시각 근거 없이는 수치 보고하지 않음 |
| **개발 중 대리 지표** | T0 → 좌석 확보 후보 요청의 브라우저 전송 시작 | 우선 후보 inputTravellers. 서버 수신·수락·보유와 구분하고 후보 판정이 바뀌면 지표도 변경 |
| 보조 지표 | 후보 요청 시작 → 첫 응답 / 전체 응답 / 업무 상태 판독 | 요청 처리 초반에 보유될 가능성을 배제하지 않음. 응답 완료를 보유 시각으로 치환 금지 |

T0는 예정 개방 기준09:00이며, 서버가 실제 허용한 시각은 별도 미확정이다. 리허설은 이미 열린 일반석의 가상T0를 쓴다. 운영의2500ms 선발사는 유지하며, API 요청도 무조건2.5초 앞당기지 않는다. 미개방 응답과 재시도 때문에 늦어지는지 별도 평가한다.

### 1.1 재설계의 성능 기준 — 2026-09-12

사용자의 목표는 개방 직후 경쟁 좌석을 확보하고 실제 결제창에 도착하는 것이다. **개발 목표는 T0+3초 이내 후보 요청 전송으로 잡는다.** 이는 5초보다 이르게 접근하기 위한 도전 목표이며 실측·확보 보장·이론적 하한이 아니다. 좌석 확보 시점이 확인되면 별도의 보유 지표로 평가한다. 3초를 못 맞추면 남은 필수 왕복과 비용을 공개하며 검증을 생략해 맞추지 않는다.

| 항목 | 기준 |
|---|---|
| T0 | 예정 개방 09:00. 실제 최초 개방 확인과 분리. 리허설은 명시한 가상 T0 |
| 개발 목표 | 후보 요청 전송 ≤ T0+3초. 초과한 실행도 모두 기록하고 목표 미달로 보고 |
| 구현 자체의 지연 예산 | 조회 시작 지연 ≤100ms, 의존 데이터 준비→다음 필수 요청 전송 합계 ≤100ms를 초기 목표로 설정. 서버/필수 검증 대기는 별도 기록 |
| 업무 성공 | 해당 여정·편명·등급·승객의 보유 상태/기한 확인과 동일 주문의 실제 결제창. 보유 의미가 불명확하면 미확인 |
| 시간의 해석 | 전송·첫 응답·본문 완료·보유 확인·인계·결제창을 분리. 전송 시각을 확보 시각으로 바꾸지 않음 |
| 성능 보고 | Windows 동일 조건 비교의 개별 실행·최대·실패 포함. 적은 표본으로 백분위 보장하지 않음 |

예산식은 `조회 시작 지연 + 조회 왕복 + 운임 왕복 + 남는 필수 검증 대기 + 로컬 처리 비용`이다. 조회/운임이 각각 2초라면 추가 대기 없이도 약4초가 필요하므로 3초 목표에 미달한다. 이때 더 빠른 실측, 사전 처리 가능한 검증, 정상 계약상 더 짧은 경로를 조사한다. 최신 조회 결과에 의존하는 운임을 추측으로 병행하거나 과거 ID를 재사용하지 않는다.

9/12 일반석 원본은 조회1.749초·운임1.397초·승객 요청6.219초 왕복을 기록했다. 이는 09시 프레스티지 성능이 아니다. 회사 Windows의 약2초 왕복은 사용자 기억이며 원본 미확인이다.

**기존 6초 마감·4.5초 하한·1.5초 여유는 철회한다.** Date 헤더는 재고 확인 시각이 아니며, [deadline.py](../../../api_booking/deadline.py)의 오프셋 구간/대체 왕복/성공 판정에는 [검토 보고서](../../../api_booking/feasibility-review-2026-09-12.md)의 결함이 있다. 이 도구와 과거 budget.json의 within을 출시/성능 판단에 사용하지 않는다. 코드 수정은 아직 하지 않았다.

경과시간은 같은 실행의 단조시계로 연결하고, 절대시각과 연결할 때 기준값·불확실성을 함께 보존한다. 시계축 불일치 시 T0 상대 성능은 판정 불가로 남기되 유효한 요청 왕복은 별도로 보고한다. Date는 보조 진단만 사용한다. 사용자 결정에 따라 운영 발사 시계는 수정하지 않는다.

현재 구현은 수집기·오프라인 분석기와 A1 메모리 주문 상태 모델까지다. **실제 API 실행/인계/영속 복구는 미구현**이다. 단계별 진행은 §7.0을 따른다.

동일 값 관측만으로 필드 의존성을 확정하지 않는다. 실제 수집에서는 boundId와 flightId가 같은 값인 사례도 있었으므로, 호출부가 사용하는 필드를 대조해 연결을 판단했다. 계정·토큰·주문 식별자 원문은 저장하지 않는다.

### 2.3 좌석 확보 요청 특정 — 확인된 범위와 경쟁 가설

| 요청 | 현재 근거 | 좌석 확보에 대한 판정 / 추가 증거 |
|---|---|---|
| awardAvailability | 항공편·등급·가용 운임과 다음 요청의 식별자를 반환 | 조회 결과만으로 보유 아님. 조회가 잠시 재고를 묶는 서버 동작까지 부정할 근거도 없음 |

| 마일리지 적용·결제 준비·NaverPay/카드 요청 | Npay는 앞서 받은 예약번호로 결제 세션을 생성하는 호출부 확인. 현대카드 연결과 일부 마일리지 적용 요청은 미수집 | 이 단계에서 재고 재검증·확정·만료 처리가 추가되는지 미확인. 결제 전 흐름 전체를 확인하고 앞 단계에서 보유가 확정됐다고 가정하지 않음 |

[사이트 호출부·해시](../../../dev-shots/api-source-2026-09-10/review.json), [실제 주문 응답 구조](../../../dev-shots/runs/20260909-171936-3c3869a0/manual_booking.json), [기록 코드](../../../dev/network_trace.py)를 대조했다. 9/9 기록은 pnr의 존재/타입만 남기며 boundList 내부10개 필드를 생략했다. 9/10 추가 수집에서 구간 status=HK를 보조 기록했지만 서버 처리 중 보유 시각·기한·상태 의미는 아직 미확인이다. 일반 유상 흐름의 createOrder(cartId)를 마일리지 inputTravellers의 증거로 섞지 않는다.

**추가 수집 순서:** 정상 일반석의 조회→운임→승객 전송→동의·마일리지→결제창 전 구간을 수동적으로 기록한다. 확인된 구간별 예약 상태/업무 코드/보유·발권 기한 필드만 허용 목록에 추가하고 의미를 사이트 코드·제공되는 공식 설명과 대조한다. 식별자는 같은 실행 안 익명 참조로 연결하고 원문은 저장하지 않는다. 각 단계 전후 같은 주문 상태를 정상 읽기 경로로 확인하며, 시험 주문의 취소·해제도 별도로 확인한다. 상태 의미를 알 수 없으면 ‘관측 코드’로만 보고한다.

재고 표시는 보조 근거다. 일치하는 편명·등급의 조회 결과를 제한된 간격으로 대조해도 다른 고객·캐시·응답 지연이 있어 우리 요청이 원인이라고 확정할 수 없다. 계측 목적으로 복수 주문을 만들거나 마지막 프레스티지 좌석을 점유하는 실험은 하지 않는다. 서버의 보유 이벤트/시각을 얻지 못하면 직접 측정 한계를 유지한다. 이후 상태 응답으로 보유가 확인되더라도 정확한 생성 시각이 없으면 ‘이 확인 시점에는 보유 상태’까지 보고한다.

## 3. 단계별 브라우저/API 구분 — 개발 계획

**기본 구조는 로그인된 Chrome 안에서 요청을 수행하는 혼합 방식이다.** 브라우저 쿠키·세션을 유지하되, 단순 fetch가 사이트 프레임워크의 인증·오류·접근 제어 처리를 자동으로 수행한다고 가정하지 않는다. 정상 요청 경로와의 동등성을 시험한다. 외부 Python HTTP 클라이언트로 전체 흐름을 바로 옮기는 방안은 우선 적용하지 않는다.

아래 ‘API’는 전환 대상으로 선정했다는 뜻이다. 구현·실사이트 동등성 시험이 끝났다는 뜻이 아니다. ‘조건부’는 해당 경계의 시험이 통과하기 전 브라우저 경로를 유지한다.

| 기존 단계 | 초기 개발 방향 | API로 바꾸는 방법 / 현재 브라우저에 남기는 이유 |
|---|---|---|
| 준비: 로그인·추가 인증·접근 대기 | **브라우저 유지** | 정상 로그인과 사이트의 접근 허용 절차를 사용. 인증·대기열을 생략하는 API 경로는 만들지 않음. 로그인 후 목표·KRW·승객 정보 준비 |
| 정시 시작·달력 재로딩 | **API 전환 대상** | 준비된 요청 조건으로 새 날짜의 항공편 조회 시작. 미개방/오류와 매진을 구분. 달력 렌더링 대기를 줄이는 것이 목적. 신규 날짜 직접 조회 조건과 세션 유지를 검증한 후에만 사용 |
| 1. 달력 날짜 선택 | **API 전환 대상** | 요청의 전체 출발일·출발지·도착지로 대상 지정. 월·일만 바꾸지 않음. 응답의 실제 노선·날짜 일치 검사 |
| 2. 검색 | **API 전환 대상** | 정상 `awardAvailability` 요청 구조로 조회. 현재 실사이트에서 관측한 currency/segmentList/travelers와 나머지 필수 설정을 완성. 아직 독립 호출 성공은 미검증 |
| 3. 좌석 등급 선택 | **API 전환 대상** | 응답에서 지정 운항사·편명 조건·등급·매진 여부를 검사하고 최신 recommendId/flightId를 선택. 초기에는 일반석만 허용 |
| 4. KRW 확인 | **준비는 브라우저, 실행 중 API 검증** | 사전 KRW 설정 유지. 조회·운임 응답의 통화가 실제 KRW인지 검사하고 USD를 KRW로 라벨만 바꿔 사용하지 않음 |
| 5. 다음 / 운임 확인 | **API 연속 처리 대상** | 실제 관측한 recommendList로 fareInformation 요청. 금액·마일리지·운항 구간·등급 검증. 정상 세션·pageTicket을 다음 필수 검증/승객 전송으로 연결. 여기서 화면 표시를 기다리는 것은 기본 설계가 아님 |
| 6. 승객 확인 | **API 전환 조건부** | 이미 준비된 승객 정보로 정상 확인 과정의 검증을 수행. 회원 검증·마일리지 잔액·승객 유형 등 실제 필요한 조건을 식별. 화면이 채워졌다는 사실만으로 확인 처리가 끝난 것은 아님 |
| 7. 연락처 확인 / 승객·주문 전송 | **API 전환 조건부** | 준비된 연락처와 승객 목록으로 실제 inputTravellers 입력 구성. 앞선 운임과 서버 세션 연결을 확인하고 한 번 전송. 응답 불명확 시 주문 상태 확인 전 재전송 금지 |
| 8. 첫 동의 | **초기 브라우저 유지** | 현재 운임·규정에 대한 실제 동의 절차. API의 대응 필드·서버 반영 여부가 미확인이라 플래그를 추측하지 않음 |
| 9. 첫 모달 스크롤 | **초기 브라우저 유지** | 기존 검증된 모달 절차 사용. 이후 순수 화면 동작으로 입증되고 필요한 고지·동의를 동일하게 처리할 수 있을 때만 전환 검토 |
| 10. 첫 모달 확인 | **초기 브라우저 유지** | 실제 동의 완료 상태가 결제 모델에 어떻게 반영되는지 추가 확인 필요 |
| 11. 위험품 등 두 번째 동의 | **초기 브라우저 유지** | 첫 동의와 별개. 한 동의로 두 절차를 완료 처리하지 않음 |
| 12. 두 번째 모달 스크롤 | **초기 브라우저 유지** | 동일한 이유. 사용자 확인이 필요한 고지·선택을 생략하지 않음 |
| 13. 두 번째 모달 확인 | **초기 브라우저 유지** | 별도의 완료 상태와 실제 반영을 검증한 뒤에만 API 전환 논의 |
| 14. 마일리지 적용 | **초기 브라우저 유지** | 실제 적용액·본인/가족 차감·부족액 처리의 요청/상태 연결을 아직 수집하지 못함. 가족정보 사전 조회로 마일리지 적용을 대신하지 않음 |
| 15. 결제수단 선택 | **선호는 사전 설정, 초기 클릭은 브라우저** | ICN 출발 Npay, 도착 한국발행 카드. 목록 API(currency/mode)는 사전 준비 후보. 현재 주문에 적용 가능한 수단인지 재확인 |
| 16. 현대카드 선택 | **초기 브라우저 유지** | 현대카드의 실제 인증 요청·폼 제출·리다이렉트 연결은 미수집. 관련 브랜드 명칭이 있는 코드만으로 실전 분기를 확정하지 않음 |
| 17. 대한항공 결제하기 | **초기 브라우저 유지, Npay 발급 API는 후속 전환 후보** | Npay 입력/응답 구조는 소스 확인. 주문·금액·콜백과 새 창 연결의 실측 동등성 확보 후 API 발급으로 교체. 현대카드는 별도 검증 |
| 제공자 창 도착·최종 승인 | **브라우저·사용자 유지** | Npay/현대카드가 요구하는 현재 결제 세션·인증 UI 필요. 도착만 읽기 판정하고 최종 승인은 사용자가 수행 |

‘브라우저 유지’는 기술적으로 영원히 API화할 수 없다는 뜻이 아니다. 현재 미확인인 요청·상태 연결을 생략하지 않기 위한 초기 범위다. API 전환 구간을 늘릴 때마다 일반석 전체 리허설을 다시 통과해야 한다.

### 3.1 우선 구조: 필요한 API를 연속 처리한 뒤 한 번 인계

`정상 브라우저 사전 준비 → 항공편 API → 목표 선택 → 운임 API → 필수 검증 → 승객·주문 API(1회) → 동일 주문 상태를 브라우저에 1회 인계 → 동의·마일리지·방향별 실제 결제창`

- 첫 목표는 좌석 확보 후보 요청까지의 **화면 표시·클릭 의존성 제거**다. 운임 뒤 승객 화면을 띄우는 방식은 연결을 연구하는 중간 시험일 수 있으나 성능 구현의 완료 기준이 아니다. 좌석 확보 관여 요청이 달리 판명되면 연속 처리 경계를 조정한다.
- 일반석에서 API 응답·서버 세션·정상 store 상태의 연결을 확인한다. inputTravellers 본문에 항공편 ID가 직접 없으므로 세션의 선택이 맞는지 입증하기 전 전송하지 않는다. 정상 프레임워크의 인증·토큰 갱신·오류 처리를 유지한다.
- 인계는 같은 실행의 검색 조건·운임·승객·주문 응답을 정상 화면 모델에 연결하는 방식이 가능한지 검증한다. URL만 이동하거나 성공 플래그만 설정해서는 안 된다. 주문 API를 UI가 다시 호출하면 실패다.
- **새 항공편/운임 재조회·재주문 없이 한 번 인계가 가능한지는 아직 미검증**이다. 재설계에서는 동일 주문의 정상 읽기를 허용하고 그 비용을 별도 측정한다. 상태 유지와 복구 가능한 인계의 우선순위는 §3.3을 따른다.
- 필수 회원·마일리지·운항 구간·등급 검증, 적용되는 안내·동의·접근 제어를 생략하지 않는다. 입력 초안이 준비됐다는 사실과 서버가 확인을 수락했다는 사실은 다르다.

### 3.2 사전 처리와 신규 응답 의존 작업

| 작업 | 처리 위치와 조건 |

| 실제 운임·세금·필요 마일리지·예약 등급·구간 검증 | 새 운임 응답 필요. 가용 잔액은 준비해도 새 필요액과의 비교는 이때 수행 |
| 승객·주문 요청 | 준비된 초안을 사용하되 최신 선택/운임 세션 및 필수 검증 완료 후1회 |
| 결제 목록·선호 수단 | currency/mode 기반 사전 준비 후보. 실제 주문에 적용 가능한지 확인 |
| 결제 세션 발급 | 현재 주문·금액·예약번호가 필요. 보유 후보 요청 전송 지표와 별도 측정; 보유에 영향을 준다는 증거가 생기면 성능 경계에 포함 |

### 3.3 재설계: 정상 상태를 유지하는 연속 실행과 동일 주문 복구

이 절은 §3의 전환 후보를 실제 개발 단위로 구체화한다. **HTTP 3회나 단계7 종료를 고정하지 않는다.** 서버 의존성과 정상 화면 상태를 유지하면서 중간 렌더링·클릭 대기를 제거한다. §3.1의 재조회 없는 인계는 최적화 후보이며, 동일 주문의 필요한 읽기 요청을 실패로 간주하지 않는다. 주문 재생성은 금지한다.

#### 실행 환경과 구성

기준 환경은 회사 PC Windows다. 연구 전용 Chrome 9242·`.api-profile`을 정상 로그인 상태로 유지한다. Python은 준비·관측·결과 저장을 담당하고, 빠른 요청 연결은 같은 페이지의 실행기가 담당하도록 설계한다. 각 API마다 Python과 브라우저 사이를 왕복하지 않는다. 운영9232/9233·시계·실전 발사 방법은 자동 교체하지 않는다. 새 연구 대기 시작도 사용자 조작을 통해서만 허용한다.

아래는 **예정 모듈**이며 현재 존재하는 실행기로 오해하지 않는다.

| 모듈 | 책임 | 구현 전 필요한 계약 |
|---|---|---|
| `site_adapter.js` | 정상 요청 호출·인증/오류 처리·요청 문맥 보존 | 실제 URL/입력/헤더 출처, pageTicket 수명, 공통 요청 변환·갱신 방식 |
| `flow.js` | 선행 데이터가 준비되면 다음 노드 실행, 단계별 검증 | 요청별 의존성·부작용·완료 조건 |

#### 개방 전 준비

1. 여정 전체 날짜·공항·편명 조건·승객 수·목표 등급·통화·방향별 결제 제공자를 확정한다. 일반석 시험은 별도 설정으로 구분한다.
2. 정상 로그인·필요 인증·KRW·승객/연락처 초안을 준비한다. 비밀번호·쿠키·주문 식별자는 로그에 저장하지 않는다.
3. 재사용 가능한 회원/가족/잔액·정적 규칙을 준비한다. 각 값에는 입력 키·관측 시각·유효 조건을 붙이며 재사용이 입증되지 않은 검증은 개방 후 필수 노드에 남긴다.
4. 요청 연결기·정상 화면 모델·계측을 준비한다. 같은 연구 세션의 다른 탭이 여정을 변경하는 것은 허용하지 않는다. 프로필 분리와 회원 서버 상태 분리는 다르므로 실제 주문을 운영과 병행하지 않는다.
5. 과거 미해결 주문이 있으면 준비 완료로 표시하지 않는다. 설정/코드 지문이 바뀌면 대기 준비를 무효화하고 사용자가 다시 확인하도록 한다.

#### 개방 후 실행

`최신 항공편 조회 → 편명/등급/재고 검증 → 운임 → 새 필요 마일리지/필수 검증 → 주문 전송 → 주문 응답 검증 → 정상 후반 흐름 → 제공자 창`

조회 전 달력 화면을 새로 그리는 것은 기본 경로에서 제거한다. 직접 조회에 필수 초기화가 있다면 사전 실행 가능 여부부터 확인한다. 최신 조회의 운임 ID가 필요한 요청은 직렬로 둔다. 병행은 서로의 입력과 서버 선택 상태를 바꾸지 않는다고 입증한 조회에만 허용한다. 기본 주문 경로는 한 개다.

각 노드의 계약은 `입력과 출처 / 최신성 / 인증 문맥 / 선행 노드 / 서버 변경 여부 / 업무 성공·실패 코드 / 화면 상태 반영 / 재시도 가능 여부 / 근거 실행ID`를 포함한다. 미확인 필드는 임의 기본값으로 보내지 않고 계약 미완료로 중단한다. 전체 응답과 목표를 확인해야 다음 변경 요청을 보낼 수 있다.

시작 지연을 줄이기 위해 실행기와 요청 템플릿은 미리 준비하지만 실제 날짜의 운임/선택 ID는 새 응답에서만 얻는다. 영속 로그 저장은 빠른 경로에서 매 요청마다 기다리지 않는다. 단, 주문 전송 의도는 전송 전에 내구성 있게 기록하며 해당 비용을 성능 예산에서 빼지 않는다.

#### 브라우저 인계는 상태 유지부터 시작

API 처리 동안에도 정상 사이트가 쓰는 선택·운임·승객·주문 모델을 정상 갱신 경로로 유지한다. 목표는 마지막에 낯선 상태를 억지로 주입하는 비용과 오류를 줄이는 것이다. 실제 갱신 경로가 외부에서 호출 가능하다는 것은 아직 미입증이며 계약 수집에서 가장 먼저 확인한다.

인계 방법은 아래 순서로 선택한다.

1. **우선안:** 정상 데이터 처리와 화면 전환을 분리할 수 있으면, 데이터 상태만 연속 반영하고 준비된 단계에서 화면을 한 번 표시한다. 화면이 뒤에서 렌더링되더라도 요청 경로가 DOM 준비를 기다리지 않게 한다.
2. **복구 가능한 대안:** 서버 주문 응답을 확인한 뒤 정상 예약/결제 재개 경로로 같은 주문을 읽어 화면에 진입한다. 필요한 읽기 왕복은 측정하며 허용한다. 결제수단·여정·승객·금액과 새 창의 동일 주문을 대조한다.
3. **판정 보류:** 위 두 방법이 불가능하면 주문 후 인계를 약속하지 않는다. 검증된 더 이른 경계에서 UI를 이어가는 비교본으로 측정하고, 더 뒤까지 API화할 정상 계약이 있는지 조사한다. 목표 시간에 미달하면 미달로 보고한다.

인계 경계는 기능 시험으로 고정한 뒤 실행한다. 09시 실행 중 처음 보는 상태를 해석해 즉석에서 경로를 바꾸지 않는다. 해당 사이트 코드가 바뀌거나 정상 상태 연결을 확인하지 못하면 연구 실행을 준비 완료로 판정하지 않는다.

#### 좌석 보유에 따른 경계 결정

| 계약 검증 결과 | 빠른 경로 범위 | 후반 처리 |
|---|---|---|
| inputTravellers 응답/정상 상태 조회로 보유와 기한을 확인 | inputTravellers까지와 필요한 검증 | 같은 주문의 동의·마일리지·결제 화면으로 이어감. 기한 내 완료 필요 |
| 보유를 결정하는 단계가 마일리지/후반 검증임을 확인 | 해당 단계까지 정상 계약을 연결하도록 확장 | 필요한 동의는 정상 절차로 처리하고 통과 조건에 포함 |
| 보유 의미를 끝내 확인하지 못함 | 후보 요청 전송까지 최적화하며 전체 흐름도 계속 검증 | ‘좌석 확보 완료’ 표시 금지. 최종 결제창까지의 기능과 대리 성능만 보고 |

보유 검증은 개발 중 판정한다. 실제 빠른 경로에 진단용 폴링을 무조건 추가하지 않는다. 정상 업무에 필요한 읽기와 실패 복구 읽기를 구분한다. 실제 실행에서는 주문 응답 검증이 끝나면 다음 정상 단계를 이어가며, 정확한 보유 시각을 알아내려고 대기하지 않는다.

#### 중단·재시도·복구 상태

기본 상태는 `PREPARED → WAITING_USER → RUNNING → ORDER_INTENT → ORDER_IN_FLIGHT → ORDER_CONFIRMED → HANDOFF → PAYMENT_READY`다. ORDER_CONFIRMED는 업무상 주문 응답 검증이며 seatHoldVerified와 별도다. 어느 상태에서든 `STOPPED`, 전송 가능성이 생긴 뒤에는 `ORDER_UNKNOWN`으로 갈 수 있다.

| 상황 | 동작 |
|---|---|
| 개방 전 조회 응답 | 미개방으로 기록. 재전송이 허용된 조회만 설정된 횟수/간격/종료시각 안에서 재시도. 서버 제한 우선, 무한 재시도 금지 |
| 매진·잘못된 여정/등급·업무 오류 | 해당 실행 중단. 다른 날짜/등급으로 자동 변경하지 않음 |
| 401/403·추가 인증·대기열 | 정상 접근 절차 확인이 필요함을 표시하고 실험 중단 |
| 429 | 서버 대기 지침을 준수. 그 사이 세션/실행 기한이 끝나면 중단 |
| 주문 전송 직전 | 실행/회원 범위 미해결 여부 확인, ORDER_INTENT 저장. 한 실행기만 변경 요청 소유 |
| 주문 전송 후 시간초과·연결 단절·비정상 본문·프로세스 종료 | ORDER_UNKNOWN. 재전송·UI의 새 주문 금지. 새 실행ID여도 같은 연구 회원의 미해결 상태가 해소될 때까지 차단 |
| 주문은 확인했으나 인계 실패 | 같은 주문의 정상 조회/재개만 허용. 신규 조회·운임으로 다시 시작하지 않음 |
| 정상 조회에서 주문을 못 찾음 | 부재 응답 한 번으로 미생성 판정하지 않음. 확인 불가를 유지하고 사용자에게 상태 인계 |
| 결제창 도착 | 방향별 새 창·현재 주문·여정·금액 검증. 최종 승인은 사용자 |

영속 기록에는 실행ID·설정 지문·단계·전송 여부·미해결 표지만 저장하고 주문 식별자 원문은 남기지 않는다. 복구는 정상 예약 목록에서 사용자/여정과 대조한다. 복구 계약이 없으면 자동 복구를 제공하지 않고 차단 상태를 명확히 표시한다. 클라이언트의 1회 전송을 서버의 정확히 1건 생성 보장으로 표현하지 않는다.

**기존 UI 기록의 한계:** 오전 승객 확인 단계는 페이지 이동 대기3.8초·요소 없음1.2초·가림0.3초를 기록했다. 그러나 요소가 없는 이유가 API 미완료일 수도 있다. [재생기 phase/markStep](../../../ke_award/recorder.js)는1초 이상 tick 공백을 합산에서 제외하고 원인별 출력도 반올림한다. 단계 ms와 원인 합계를 그대로 더하거나 네트워크 시간에서 전부 빼면 중복/누락이 생긴다. 현재 자료로 순수 렌더링·클릭·서버 대기를 정확히 완전 분리할 수 없다.

운임 응답 뒤 가족 조회1.932/1.970초, 카드정보0.945/1.050초, 회원 검증1.110/1.236초가 관측됐다. 모두 삭제 가능한 대기라고 볼 수 없다. 새 운임과 잔액 비교, 예약 등급 검사는 호출부에 명시돼 있다. 화면 이동과 API 호출이 중첩되므로 각 API 시간을 단순 합해 절감량을 주장하지 않는다.

| 비교 방식 | 줄일 후보 | 남는 비용 / 성과 판단 |
|---|---|---|
| 기존 브라우저 최적화 | 전체 화면 안정 대신 목표 요소의 준비 완료 조건 사용, 불필요한 재탐색/재확인 감소 | 현재 DOM 전환·필수 API는 필요. 표시된0.573~3.743초·5.525~8.136초 중 실제 제거 가능분을 측정. 브라우저가6초에 불가능하다고 단정하지 않음 |

## 6. 봇 탐지·접근 제한 검토

### 6.1 확인한 사실과 한계

- 현재 연구 브라우저의 정상 페이지에서 **Queue-it 스크립트 로드**를 확인했다([창 상태](../../../dev-shots/api-source-2026-09-10/final-lab-state.json)). 공급사의 [공식 개발 문서](https://queue-it.com/developers/bots-abuse-management/)는 대기열·접근 규칙·봇/행동 분석과 다른 방어 계층의 결합을 설명한다. 이것이 대한항공에 모든 기능이 활성화됐다는 증거는 아니다.
- 동일 공개 JS 주소가 정상 Chrome에서는 로드됐으나 별도 PowerShell HTTP 요청에서는403이었다. Python에는 인증서 검증 실패도 별도로 있었다. 브라우저와 외부 클라이언트의 호환성 차이이며 **403 원인이 봇 탐지라고 확정한 것은 아니다.** 차단 응답 뒤 우회 설정이나 반복 요청으로 돌파하지 않았다.
- 정상 UI 수집의 대상 API10건은200, 마지막 화면에서 명시적 접근 차단·CAPTCHA·대기열 문구를 찾지 못했다. **독립 API 예매의 봇 미탐지, 계정 제재 없음,09시 통과를 입증하지 않는다.**
- [대한항공 이용약관](https://www.koreanair.com/contents/footer/terms-and-policies/terms-of-use?hl=ko)의 제5조·제16조는 서비스 방해 등에 대한 제한과 허용되지 않은 정보/프로그램의 무단 송신 등을 다룬다. 확인한 약관에서 이 개인 자동화 방식을 명시적으로 허용한다는 근거는 확보하지 못했다. 기술적으로 응답이 온다는 사실과 이용 허용 여부는 다르다.

### 6.2 개발·시험에 반영할 처리

| 신호 | 처리와 기록 |
|---|---|
| 401 / 로그인 이동 | 세션·인증 문제로 기록하고 해당 API 실행 중단. 사용자 로그인 경로 사용 |
| 403 / 접근 거부 / CAPTCHA / 대기열 | 해당 실험을 멈추고 정상 사이트 절차로 확인. 접근 통제·서명·봇 검사를 생략하는 경로는 개발하지 않음 |
| 429 | 서버 제한으로 기록, Retry-After 등 명시된 대기 지침 준수. 동시 요청 증가나 즉시 반복 금지 |
| HTTP200 + 업무 오류 / 비JSON | 유효 항공편·운임·주문 결과로 세지 않음. 오류 단계와 응답 구조 기록 |
| 주문 요청 시간 초과 | 수락 여부 불명확 상태. 주문 상태 확인 전 자동 재전송 금지 |
| API 사용 후 브라우저도 실패 | 해당 세션의 앞선 오류·시각·경로를 연결해 보고. 새 프로필/IP/계정으로 차단 회피하지 않음 |

속도 개선은 요청 폭주가 아니라 **필요 없는 화면 대기·재조회 감소**로 검증한다. 정상 브라우저 세션 사용도 봇 탐지 면제를 보장하지 않는다. 최초 일반석 시험에서는 독립된 한 흐름으로 시작하고 운영 계측의 요청 간격을 연구에 임의 적용하지 않는다.

3. **시간 계측의 남은 공백을 채운다.** 요청 시작/전송/첫 응답/전체 응답·Python 콜백·단조 경과·미완료 요청·실행ID/코드 해시는 구현했다. 종료가 ended여도 allTrackedRequestsRecorded와 요청 원장을 따로 읽는다. --reference-at은 시간대가 있는 사용자 기준 시각일 뿐 NTP/서버 개방 검증이 아니다. 요청 구성 시간·DOM/클릭별 사건·전체 여정 일치 검증 결과는 아직 별도 보강 대상이다.
4. **허용 목록 밖 요청과 실제 결제창 공백을 보강한다.** 마일리지 적용·동의의 서버 반영 여부·현대카드 경로를 소스와 정상 흐름에서 확인한다. 전체20건 기록이 사이트의 모든 요청 수집을 뜻하지 않는다. 새 시험이 필요하면 이전 주문 상태를 먼저 확인하고, 같은9242 정상 로그인·일반석·방향별 결제창까지 순차 수집한다. 최종 승인은 하지 않는다.
5. **증거로 연속 처리 순서를 갱신한다.** 현재 확인한 조회→운임→승객/주문→Npay 연결에 필수 검증·서버 선택 세션·동의 경계를 더한다. 보유 시각이 확인되지 않으면 대리 지표를 유지한다. 이후 §3·§5의 독립 실행·1회 인계·비교 시험으로 넘어간다.

수집 단계의 완료는 ‘수집기가 실행됨’이 아니라 **전체 흐름의 증거와 남은 공백이 식별된 상태**다. 독립 API 예매 완성이나 실전 적용 승인은 아니다. 이후 순서는 **일반석 API 연속 처리 → 동일 주문1회 인계 → 세 방식 비교·전체 결제창 검증 → 사용자 실전 적용 판단**이다.

### 7.3 확인된 명령과 산출물

모든 명령은 Astra 루트에서 실행한다. 아래 날짜·경로는 보존된 증거 예시다.

**기준 환경은 Windows다.** 9/14 실전이 회사 PC에서 돌아가므로 새 코드는 Windows에서 동작해야 한다. `deadline.py`는 표준 라이브러리만 쓰고 경로를 `pathlib`로 다룬다.

```powershell
.\.venv\Scripts\python.exe api_booking\deadline.py dev-shots\runs\<예매실행> --observer dev-shots\runs\<계측실행>
.\.venv\Scripts\python.exe api_booking\test_deadline.py
```

Mac 작업분은 같은 인자에 실행기만 다르다.

```bash
# 저장된 로그 분석. 사이트 접속 없음; 결과는 콘솔 출력
./.venv/bin/python api_booking/analyze.py dev-shots/runs/20260909-105704-a2210db5
# 과거 분석 재현용만. 현재 마감/성능 판정에 사용 금지 (§1.1)
./.venv/bin/python api_booking/deadline.py dev-shots/runs/20260912-084745-849705f0 --observer dev-shots/runs/20260912-084914-7c888635
# API 코드 변경 후 로컬 시험
./.venv/bin/python api_booking/test_analyze.py
./.venv/bin/python api_booking/test_deadline.py
./.venv/bin/python api_booking/test_collect.py
./.venv/bin/python api_booking/test_collect_browser.py
```

아래는 **실사이트 수집을 진행할 때만** 사용한다. 정상 로그인/추가 인증은 연구 프로필에서 수행하고 운영 프로필을 복사하지 않는다. 브라우저 실행과 수집은 순서대로 시작하며 수집 중 정상 UI 동작을 별도로 수행한다.

```powershell
# Windows: 연구 Chrome이 없을 때만 실행 또는 소유권 확인 후 재사용
& .\api_booking\open_lab.ps1
# 요청을 발생시키기 전에 수집 시작. 최대900초; 이 명령은 클릭/주문을 하지 않음
.\.venv\Scripts\python.exe api_booking\collect.py --seconds 300 --origin ICN --destination CDG --target-date 2027-09-04
```

```bash
# macOS: 같은 순서. --status 는 열지 않고 소유 상태만 읽는다
./api_booking/open_lab.sh --status
./api_booking/open_lab.sh
./.venv/bin/python api_booking/collect.py --seconds 300 --origin ICN --destination CDG --target-date 2027-09-04
```

`open_lab.sh`는 9242를 점유한 프로세스의 명령줄에 **우리 포트와 `.api-profile`이 각각 인자 하나로 있는지**까지 확인한다. 부분 일치가 아니라 앞뒤 공백 경계를 대조하므로 `.api-profile-other` 같은 다른 프로필은 우리 것으로 인정하지 않는다. 종료 코드는 **0 준비됨 / 1 없음·준비 실패 / 2 알 수 없는 프로세스가 9242 점유**다. 어떤 프로세스도 종료하지 않으므로 정리는 소유권을 확인한 뒤 해당 PID만 사용자가 처리한다. `dev/astra_browsers.sh`(운영 9232/9233)는 이 소유권 검사를 아직 하지 않는다. 찬 시작이 10초를 넘길 수 있어 준비 대기는 30초다.

**2026-09-12 Mac 확인:** 열기·재실행 재사용·`--status`·다른 프로필(`.api-profile-other`)을 띄운 9242 거부(종료 코드 2, 열지도 끄지도 않음)까지 실제로 확인했다. `collect.py`가 붙어 20초·10초 관측으로 `contracts.json`(state=ended·오류0·rows0)을 남겼다(`20260912-215622-553c9079`, `20260912-220053-5065c489`). 로그인·정상 UI 조작은 하지 않았으므로 **대상 API 행은 0이며 실제 계약 수집이 아니다.** `--status`의 ‘소유하지만 CDP 미준비’ 분기는 구간이 짧아 실제로 재현하지 못했고 코드 검토로만 확인했다. SHA256: open_lab.sh `c0c489d72219b67a16ea117e82bba0045a4e896704ff397aafb268032b00eb9e`.

수집기는 시작 시 `dev-shots/api-capture/<시각>/`를 출력하고 **contracts.json**을 주기적으로 저장한다. 기존 result.json은 별도 분석 요약이며 자동 생성 산출물로 기대하지 않는다. publicSources는 수집 중 포착한 파일만 포함한다. 위51개 공개 소스는 별도 추출 자료이므로 collect.py 한 번으로 동일 목록이 재생성된다고 가정하지 않는다. 진입점·본문 필드·노선/날짜를 확인하지 않은 응답은 매진·수락으로 판정하지 않는다.

`--target-date`·노선은 실행 시 공통 일정/실제 운항과 대조한다. 선택 사항인 `--reference-at`은 시간대가 포함된 ISO 기준 시각이며 자동 NTP 보정이나 UI 시작 이벤트를 뜻하지 않는다. 수집기의 기록 완료와 실제 결제창·주문 해제 판정은 별도다.

현재 계획과 재개 절차는 이 문서, 최신 상태/과제는 NOW, 운영 명세는 상위 README에만 관리한다. 보관 문서의 오래된 순서·속도 가정으로 현재 계획을 되돌리지 않는다.
