# 2026-09-09 예매·계측 실패 원인 감사

대상: 2027-09-04 FCO → ICN, 프레스티지 성인 1명. 실행: `20260909-085207-c8fdbeae`.

## 결론과 책임

**핵심 문서가 없어서 기존 성공 경로를 몰랐던 것이 아니다. Astra가 핵심 문서를 읽고도 검증되지 않은 대체 경로를 실전에 채택했고, 계측기의 첫 응답 지연 개선을 끝내지 못했다.** 분리 후 Claude의 계측 개선 커밋을 재대조·반영하지 않은 누락도 있다.

확정할 수 있는 책임은 다음과 같다.

1. 달력 새로고침과 날짜 미개방 시 재시도 경로를 예매 기본에서 제외했다.
2. 새 API 응답과 DOM 버튼 활성화를 같은 것으로 취급했다. 목표 날짜 버튼이 계속 비활성이면 달력으로 복귀하는 자동 복구가 없었다.
3. 회귀 시험에서 테스트 코드가 버튼을 직접 활성화했다. 사이트가 실제로 버튼을 활성화하는지는 검증하지 않았다.
4. 이미 열린 날짜의 일반석 리허설 결과로 신규 개방일의 날짜 전환 경로를 실전에 채택했다. 차이를 문서에 적었지만 채택을 막는 기준으로 사용하지 않았다.
5. 계측기의 반복 조회 주기와 첫 표본 지연을 분리해서 개선하지 않았다. 전날 +7.277초를 관측하고도 첫 표본 지연을 해소하지 않은 상태로 오늘 실행했다.
6. 요청 전송·수신·기록 시각과 오류 응답을 자동 결과에 충분히 보존하지 않았다. 이번에는 살아 있던 브라우저에서 사후 수집해 지연을 분해할 수 있었다.
7. 정체 후 복구 시도도 늦었고 부적절했다. 비운항일인 09-02를 기준일로 선택했으며, recorder 일시 정지와 감독 프로그램 사이의 복구 절차도 없었다.

로그인 실패, 발사 지각, 브라우저 오류 종료, 계측기 실패 전파가 오늘 예매 정체의 직접 원인은 아니다. 이 항목들을 고친 것이 날짜 전환 성공을 보장하지는 않는다.

## 2. 오늘 예매가 멈춘 직접 원인

08:55 준비 검사에서 양쪽 READY가 통과했고, 예매는 보정 시각 09:00:00.099에 발사했다.

1. 09-01 기준일 조회는 약 1.75초에 완료됐다.
2. 오픈 약 +1.85초에 기록된 API 날짜 목록에는 09-04의 일반석·프레스티지 운임이 생겼다. `emptyFare=false`, 프레스티지 `soldOut=false`였다.

API 날짜 목록의 프레스티지 가능 신호는 중요한 단서다. 그러나 이것은 날짜별 운임 목록이며 상세 잔여석 수나 주문 수락은 아니다. “Astra가 제대로 클릭했으면 반드시 확보했다”, “정확히 +1.85~7.345초 사이에 모두 판매됐다”까지는 입증하지 않는다.

### 복구 대응에서 추가로 잘못한 점

## 3. 시험이 왜 이 결함을 잡지 못했나

`test/test_departure_live.py:32`는 300ms 기다린 후 테스트 코드가 직접 버튼에 `-active` 클래스를 넣고 텍스트를 “선택 가능”으로 바꾼다.

따라서 통과한 것은 **“버튼이 누군가에 의해 활성화되면 recorder가 진행한다”**였다. 검증해야 했던 **“기준일 API 재조회가 실제 사이트의 새 목표일 버튼을 활성화한다”**는 성질을 시험하지 않았다. 실제 실패 조건은 API는 바뀌고 DOM은 비활성으로 고정되는 경우인데, 이를 시험에서 제거했다.

전날 14시 시험에서 API 날짜 목록 범위와 DOM 날짜 띠 범위가 서로 다르다는 현상도 이미 확인했다. 당시 수정은 월 경계의 날짜 위치 대조에 집중했고, **버튼의 활성 상태도 과거 상태로 남을 수 있는지**를 확인하지 않았다.

전체 결제창 17/17을 통과한 `132652-64e3063d`는 이미 열린 08-28 일반석이었다. 이후 날짜 띠 준비·park 경로를 추가한 최신 전체 리허설 `145224-51480651`은 브라우저 종료로 실패했다. 그 상태에서 새 경로를 실전에 채택했다. “신규 개방일은 미검증”이라고 적는 것만으로 충분한 검증이 되지는 않는다.

## 5. 첫 계측 표본이 왜 여전히 +7.345초인가

이번 감사는 새 조회를 보내지 않았다. 살아 있던 Astra 9233 페이지의 Resource Timing과 기존 KE_PROBE 메모리를 읽고 별도 파일로 보존했다. 브라우저 시각에는 당시 실행에서 측정한 NTP offset +0.047967초를 적용했다. 표의 +값은 09:00 기준이다.

| 시점 | 실제 사건 | 근거 |
|---|---|---|
| -2.500초 | 계측기 선발사, 달력 새로고침 시작 | watch.log 및 시계 보정 |
| +0.555초 | `calendarFareMatrix` 요청 전송 | Resource Timing requestStart |
| +2.174초 | 달력 API 응답 수신 완료 | Resource Timing responseEnd |
| +3.910초 | recorder idx>=2를 “조회 화면 도달”로 기록 | watch.log. 검색 단계 진행 지표이며 실제 좌석 데이터 준비 아님 |
| +5.533초 | 목표일 `awardAvailability` 최초 요청 전송 | Resource Timing requestStart |
| +7.209초 | 최초 좌석 API 네트워크 수신 완료 | Resource Timing responseEnd |
| +7.345초 | 페이지 probe가 응답을 기록. 프레스티지 0석 | KE_PROBE 응답 시각 + offset |
| +8.277초 | Python이 첫 표본 로그를 남김 | watch_seats.json의 at + offset |
| +8.280초 | 첫 reAsk 요청 시작 | Resource Timing fetch 시작 |

**7.345초 중 약 5.53초는 좌석 요청을 보내기 전까지다. 좌석 API 호출 자체가 7초 걸린 것이 아니다.** 최초 좌석 요청의 전체 자원 소요시간은 약 1.678초이고, 네트워크 완료 후 probe 기록까지 약 0.136초가 있다.

달력 응답 완료(+2.174)부터 좌석 요청(+5.533) 사이 약 3.359초에는 날짜 선택/검색/페이지 전환/사이트 초기화가 들어 있다. 초기 자원 기록에는 +3.63~5.03초의 언어·페이지 정보 요청 묶음도 있다. 이 구간 전체를 순수 서버 처리시간, 또는 우리 클릭 대기시간이라고 단정할 수 없다. 세부 의존 관계를 밝힐 추적 기록은 이번 실행에 없다.

### “0.2초 조회” 설명의 실제 의미

Claude 커밋 `c76bb14` 메시지는 다음과 같이 정정했다.

> “0.2초마다 찌른다”는 내 설명이 틀렸다. READ 반복은 브라우저에 이미 쌓인 응답을 다시 읽는 것이고, 서버에 새로 묻는 곳은 reAsk 뿐이다.

## 6. 계측 성공 판정에도 빠진 내용

원본 브라우저에는 목표일 award 응답이 **24건** 있었다. 그중 **20건이 좌석 표본**으로 저장됐고, 나머지 4건은 다음 오류 응답이었다.

| 오픈 후 | HTTP 상태 | 응답 본문 code | 결과 |
|---|---|---|---|
| +17.864초 | 200 | 503 | 항공편 목록 없음 |
| +18.776초 | 200 | 503 | 항공편 목록 없음 |
| +19.840초 | 200 | 503 | 항공편 목록 없음 |
| +20.853초 | 200 | 503 | 항공편 목록 없음 |

HTTP 503이 아니라 **HTTP 200 응답 안에 code=503**이었다. 오류 발생 원인이 트래픽 제한인지 일시적 서비스 장애인지는 이 기록만으로 구분할 수 없다. 더 잦은 요청이 해법이라고 단정하지 않는다.

현재 keCabin은 목표일 항공편이 없는 최신 응답을 건너뛰고 과거 정상 응답을 찾는다. 표본 저장기는 동일한 responseAt을 중복 저장하지 않으므로, 4건이 0석 표본으로 둔갑하지는 않았다. 그러나 **오류 사건 자체가 최종 watch 보고서에 남지 않았다.** +17.048초 다음 정상 표본이 +27.585초로 벌어진 이유가 파일만 보면 드러나지 않는다.

또한 `ok=bool(rows)`이므로 표본이 하나라도 있으면 성공이다. 이 값은 첫 관측의 적시성, 1초 간격 충족률, 오류 비율, 1→0 포착 성공을 보장하지 않는다. 직전 답변의 “계측 정상 종료”는 프로그램 종료 의미였고, **사용자가 원하는 소진 시점 계측 성공으로 표현할 수 없다.**

## 8. 문서를 다시 다듬을 때 필요한 기준

이번 감사에서는 운영 코드를 수정하거나 추가 주문을 생성하지 않았다. 다음은 승인 요청이 아니라 이후 문서·구현 검토의 기준이다.

1. **기존 성공 경로를 기준본으로 명시:** 달력, lead=2500ms, 미개방 재조회, 목표일 확인, 통화/등급, 주문/약관/카드. 실험 경로를 기본 경로와 섞지 않는다.
2. **현재 유효한 금지·제약은 현재 FACTS에 유지:** 과거 보관본으로만 보내지 않는다. 변경하려면 반증 시험과 적용 범위를 붙인다.
3. **신규 날짜 조건을 강제:** API 갱신/DOM 비활성 고정, 신규일이 없었다가 생김, 자동 복귀 실패를 각각 재현한다. 테스트 코드가 버튼을 켜 주는 시험을 사이트 갱신 검증으로 인정하지 않는다.
4. **예매와 계측의 서로 다른 합격 기준:** 예매는 목표일 주문/실제 결제창, 계측은 최초 목표일 응답 시각·요청 간격·오류·소진 관측 여부. 프로세스 ok만으로 합격시키지 않는다.
5. **계측 요청별 기록:** 요청 ID, 목표일, 전송, 네트워크 수신 완료, probe 기록, 파일 기록, HTTP/본문 오류, 다음 재시도. 0.2초 읽기와 1초 요청을 별도 항목으로 쓴다.
6. **병행 개발 변경 대조:** 분기 기준, 상대편 중요 수정, 반영 여부, 빌드 해시, 마지막 전체 시험 해시를 실행 전에 한 표로 확인한다.
7. **실행 중 복구 계약:** 짧은 정체 감지, 실제 선택 가능한 정상 날짜/달력 복귀, recorder와 감독 프로그램의 조정, 중복 주문 방지. 외부 pause가 실패 종료로 오인되지 않게 한다.
8. **예상 속도보다 실제 근거 우선:** 첫 요청이 +5.53초에 나가는 계측기를 “1초 계측 준비”로 부르지 않는다. 0.2초라는 값에는 반드시 잰 구간과 원본을 붙인다.
