## 속도 개선 순서

- 목표 지표를 클릭 완료가 아닌 inputTravellers 요청 전송, 응답 및 주문 성공 확인 시각으로 구분한다. dry는 해당 요청 전 정지하므로 실제 선점 시간을 재지 못한다.
- 경쟁 좌석 소진은 마지막 양수 표본과 첫 0 표본 사이의 구간이다. 첫 표본부터 0이면 소진 시각을 모른다.
- 현재 엔진은 이미 페이지 내부 JavaScript와 60ms timer/MutationObserver를 쓴다. Python의 0.2초 조회는 상태 관찰이다. 언어 변경이나 무조건적인 sleep 제거는 우선순위가 낮다.
- 실행 사용자, Python/Playwright/Chrome 버전, 프로필, 창 크기, 네트워크 상태, 실행물 해시를 기록하고 고정한다. 현재 requirements.txt의 >=만으로는 재현되지 않는다.
- 네트워크 이벤트와 request.timing/requestfinished, 렌더 기록으로 필수 요청과 화면 대기를 분리한다. 실제 서버 내부 시간은 서버 자료 없이 확정하지 않는다.
- 브라우저 세션을 유지하고 페이지 안에서 필요한 정상 요청을 수행하는 혼합 방식이 조사 가치가 있다. 조회 또는 느린 한 단계부터 검증한다. 최신 토큰, 요청 순서, 응답의 화면 반영, 정상 결제 화면 연결이 검증 조건이다. 주문 요청은 타임아웃만으로 중복 전송하지 않는다.
- 브라우저 밖 HTTP 방식은 쿠키 공유만으로 해결되지 않는다. IBE-AP.1001 실패가 TLS 지문 때문이라는 기존 문서의 원인 단정은 근거가 부족하다. 세션/토큰/순서 등도 원인 후보이며 접근 제한을 우회하지 않는다.
- 모바일 웹 측정만으로 네이티브 앱 속도를 결론 내릴 수 없다. 앱 또는 클라우드 이전의 속도 이득도 같은 조건에서 측정하기 전에는 미확인이다.
