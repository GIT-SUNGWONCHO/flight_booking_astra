# 실측 사실 (koreanair.com)

한 줄 = 한 사실 + 잰 날짜. 추측은 여기 안 들어온다 — 그건 BACKLOG 다.
틀린 것이 밝혀지면 그 줄을 고치고 `(구: …)` 를 뒤에 남긴다. 지우지 않는다.
상한 90줄. 넘으면 코드가 더 이상 의존하지 않는 사실부터 지운다.
마지막 확인: 2026-09-03

## 오픈 규칙
- 9시에 열리는 출발일 = **실행일 + 360일**. (2026-09-02 09:00 에 2027-08-28 이 열림)
- 매일 09:00 KST 에 하루치씩 열린다. 08:59 에는 그 날짜를 고를 수조차 없다.
- **화면은 저절로 바뀌지 않는다.** 08:5x 에 그려진 달력/날짜 띠를 가만히 보고 있으면
  09:00 이 지나도 그 날짜가 나타나지 않는다. 새로고침해야 다시 그려진다. (09-03)

## 경쟁 (가장 비싼 사실)
- 인기 노선 **프레스티지는 1석**이다. 승자독식. (09-02 실전, FCO)
- **10초 안에 결판난다.** 7단계 도달 10초(역대 최고)로도 졌다. (09-02)
- 그 10초 중 9초가 KE 서버 렌더·화면전환. 우리 대기는 1초대 — 브라우저로는 더 못 줄인다.
- **결승선은 결제하기가 아니라 7단계(연락처 2번째 확인)** 다.
  `POST booking/traveller/inputTravellers` 에서 orderId 가 생기고 그때 좌석이 빠진다.
  그 호출 자체가 서버에서만 4~6초 걸린다 — 못 줄인다. 8~17단계는 느려도 무관하다.
  버리면 hold 는 자동 해제된다. (08-29, 09-03 관찰)
- 좌석 수는 7단계까지 안 가도 조회 응답에 있다:
  `awardAvailability` → `commercialFareFamilyList` → `KEBONUSPR.seatCount/soldout`.
  KEBONUSPR=프레스티지, KEBONUSEY=일반석. `"9"` 는 9석 이상이라는 상한값이다.
- 단계별 총 시간 중 서버 몫: 검색 6%, 5.다음 62%, 7.확인 27%. 나머지는 렌더·부수 호출
  (회원정보·수하물정책 등 예약과 무관한 것). 줄일 수 있는 구간은 여기다. (09-03 관찰)

## 화면 구조
- **달력의 조회 버튼 라벨은 "검색"** (steps.json 2단계). 조회 화면 위젯의
  "항공편 검색"(`#flight-widget__btn`)은 **다른 버튼**이다. 이걸 몰라 4사이클을 태웠다. (09-03)
- 달력은 **두 달을 나란히** 그린다. 일자만 맞춰 첫 일치를 고르면 이른 달을 집는다
  → `#month{YYYYMM}` 안에서만 찾는다 (`util.findPickerDate`). (09-03, 이것으로 하루 날림)
- 예약 가능한 날에만 `-available` 이 붙는다. 09:00 에 하나 늘어난다.
- **달력 창은 새로고침하면 앞으로 밀린다.** 그래서 '최신 오픈일' 이 아닌 중간 날짜를
  목표로 하면 창 밖으로 나가 영영 못 찾는다. 09:00 목표는 항상 최신일이라 해당 없다. (09-03)
- 날짜칸 = `kds-dateinput` / `[class*="ui-dateinput__host"]`. 감싸개 `div.-dateinput` 를
  누르면 달력이 안 열린다 — 다른 후보를 품지 않은 가장 안쪽만 쓴다. (08-27)
- 달력 데이터는 `POST ap/booking/avail/calendarFareMatrix` 하나. 새로고침 후 **맨 마지막**에
  나가고 지연이 3.68 / 3.92 / 4.33초 → 선발사(lead) 2500ms 의 근거. (08-29)
- 로딩 가림의 정체 = `div.loading.-active` (부모 `KE-LOADING-SPLASH`, "진행중 잠시만").
  KE 처리 시간이라 줄일 게 없다. (09-02)
- 잔여석은 HTML 에 없다. API 응답으로 그린다 — 화면을 뒤져도 안 나온다.
- 헤더·위젯이 전부 shadow DOM 이라 `body.innerText` 로는 로그인 여부조차 false 로 보인다.
- 창 폭 **1400px 미만이면 모바일 레이아웃** — 셀렉터도 라벨도 통째로 달라진다.
  위험품 모달의 [아래로 스크롤] 버튼이 아예 없다. (08-28)

## 로그인 (09-04 에 이것으로 09:00 을 통째로 잃었다)
- **로그인 화면에는 탭이 둘이다** — `아이디` / `스카이패스 번호`. 기본은 `아이디`.
  스카이패스 번호를 그냥 넣으면 "일치하는 회원정보가 없습니다" 가 뜬다.
  탭은 `button[role=tab]`, 고른 것에 `aria-selected=true` + `-active`.
  탭을 바꾸면 **입력칸이 새로 그려진다**. (09-04)
- 로그인 입력칸의 id 는 **매번 바뀌는 해시**(`textinput-051db3f4bb092a`) — 잡으면 안 된다.
  보이는 `input[type=text]` / `input[type=password]` 가 각각 하나뿐이라 타입으로 잡는다.
- 계정이 둘이다: **9222=와이프 스카이패스(번호+비밀번호)**, **9223=본인(네이버 연동)**.
  스카이패스가 실패해도 네이버로 넘어가면 안 된다 — **다른 사람으로 로그인된다.**
  값은 `.env` 에만 둔다(저장소에 안 들어간다). 형식은 `.env.example`.
- **KE 세션 쿠키는 크롬을 끄면 사라진다.** 그래서 PC 를 껐다 켠 아침에는 **항상**
  네이버 연동 로그인을 다시 한다. 크롬이 켜져 있던 낮에는 그 단계가 없다.
  → 낮에 하는 시험은 로그인 경로를 아예 안 탄다. 아침 조건이 아니다. (09-04)
- **로그인 직후에는 '마일리지 예매' 전환이 붙지 않는다.** 클릭은 요소를 찾아
  누르므로 "성공" 으로 찍히는데, 위젯이 로그인 뒤 다시 그려지며 현금 모드로
  되돌아간다. 검색하면 `/booking/calendar-fare`(현금, 원화 표시)로 간다.
  완전히 새 크롬에서 실측: 1차(로그인 있음) 실패 / 2차(로그인 없음) 성공,
  차이는 로그인 단계 하나뿐이었다. → `setup.py` 는 로그인을 했으면 홈을 다시 연다.
- 네이버 자동 로그인은 `NID_AUT`/`NID_SES` 쿠키로 된다. 이게 없으면 비밀번호를
  물어 자동화가 멈춘다. **쿠키를 지울 때 도메인을 반드시 좁힐 것** —
  `clear_cookies()` 를 그냥 부르면 네이버 세션까지 날아간다. (09-04 에 9222 를 이렇게 망쳤다)

## 세션 / 페이지 수명
- **조회 화면(`/booking/select-award-flight/departure`)은 새로고침하면 죽는다.**
  `pageTicket` 이 깨져 "정상적으로 처리되지 않았습니다" 가 뜨고 날짜 띠가 사라진다. (09-03)
- 달력 화면은 새로고침을 견딘다. 그래서 09:00 경로는 달력이 기본이다.
- 조회 페이지 주소에 날짜가 없다(`/departure` 뿐). 주소로 뛰어드는 길은 없다.
- 검색은 **항상 달력으로** 간다. 조회 화면은 달력에서 날짜를 누르고 [검색] 을 눌러야 간다.
  "가까운 날짜 함께 조회" 체크박스는 그 갈림길이 아니었다. (09-03)
- 크롬을 갓 띄운 직후 첫 셋업은 자주 실패하고 두 번째에 된다. 재시도하면 된다. (09-03)
- **세션이 망가지는 것과 IP 차단은 다르다.** 한 프로필(9223)에서 조회가 계속
  "정상적으로 처리되지 않았습니다" 로 실패할 때, 같은 조회가 다른 프로필(9222)에서는
  정상이었다. 차단이 아니라 그 세션만 깨진 것이다 — 크롬을 다시 띄우면 풀린다.
  판정법: **다른 포트에서 같은 조회를 한 번 해본다.** (09-03)
- 위젯 날짜가 운항하지 않는 요일이면 검색이 `/booking/search` 로 튕기고 같은 문구가
  뜬다. 문구만 보고 차단이라 단정하지 말 것. (09-03)
- 같은 프로필의 여러 탭으로 여러 노선 동시 진행이 된다 — 세션이 서로를 덮지 않는다.
  탭0=CDG / 탭1=FCO 동시 발사, 둘 다 17/17 완주, 결제창 각각 열림. (08-30)

## 노선
- **로마(FCO)는 양방향 모두 월·수·토.** 파리(CDG)는 매일. (09-02, 달력 예약가능일 전수 확인)
- 유럽발 가능. 위젯 `ui-fromto__button -order1`=출발지 / `-order3`=도착지.
  후보는 **`ui-autocomplete__option` 을 먼저** 고른다 — 코드가 든 아무 요소나 누르면
  "여정 1 출발지 SEL - 도착지 FCO" 같은 여정 요약을 눌러버린다. 고른 뒤 값이 실제로
  바뀌었는지 검증한다. (09-02)
- 편명으로 대한항공/외항사를 못 가른다 — `KE5901` 은 에어프랑스 운항이다.
  화면의 "대한항공 운항" 표기로 가른다. 코드셰어를 고르면 5단계 뒤 추가 팝업이 낀다.

## 결제 구간
- 좌석 등급을 바꾸면 통화가 USD 로 되돌아갈 수 있다. `#currencyBtn` → KRW → **[적용]**.
  적용을 누르면 사이트가 화면을 처음부터 다시 그린다(`restartFrom=0` 의 이유). (08-27)
- 동의는 항목마다 모달이 따로 뜬다. 각각 끝까지 스크롤 + 확인. 두 모달이 같은 `#btnConfirm`.
- 마일리지 결제는 `#btnAwardUseMileageApply`(적용)가 필요하다.
- 가는 편에는 네이버페이가 있고 **오는 편에는 없다** → 한국발행 신용/체크카드 폴백.
  카드 종류는 네이티브 `<select>`(`#sel-korCardCompany`) — 클릭으로 못 고른다. value+change.

## 크롬
- 크롬은 가려진 창의 **페이지 전체**를 늦춘다(우리 코드만이 아니라 KE 자바스크립트도).
- **Playwright 는 스로틀링 끈 플래그로 크롬을 띄운다** → 테스트에서는 이 문제가 절대
  나타나지 않는다. 사람 크롬과 갈라지는 지점이라 눈으로 확인해야 한다.
- `.cmd` 의 `start` 로 크롬을 띄우면 **작업 스케줄러가 실행할 때 붙지 않는다.**
  `Start-Process` 로 직접 띄운다. (09-02)

## 막다른 길 — 다시 시도하지 말 것
- **API 직접 호출(브라우저 밖)**: 조회 요청을 그대로 재현하니 `IBE-AP.1001` 거부.
  쿠키를 복사해도 TLS 지문·봇 방어를 통과 못 한다. 마일리지 계정으로 할 일이 아니다. (08-29)
  (브라우저 *안*에서 페이지가 자기 요청을 되쏘는 것은 다른 이야기다 — `probe.reAsk()`.)
- **조회 화면 딥링크**: pageTicket 이 흐름 순서를 강제한다. 닫혀 있다.
- **테스트 계정**: 0마일이면 마일리지 예매 화면에 못 들어가 정작 중요한 구간을 못 밟는다.
- **라벨 추측 클릭 엔진**: 재생과 충돌해 7단계를 10초 지연시켰고 결제 후 팝업을 치웠다. 제거됨.
- **모바일 웹**: 별도 사이트가 아니라 같은 반응형이다. 랜딩 3.2초로 데스크톱과 동일,
  loadMs 는 오히려 더 걸린다. 같은 API 라 이득 없다. (09-02 측정)
- **실사이트 시험 과다**: 하루에 많이 돌리면 사이트가 조회를 거절한다(20분 전 되던
  날짜도 `/booking/search` 로 튕김). 하루 예산이 있다고 생각할 것. (09-03)

## 아직 모른다 (→ BACKLOG)
- 남들이 몇 초에 채가는가. `seatCount` 1→0 시각. 계측 중 — "경쟁이 되는가" 의 유일한 답.
- 요청만 직접 쏘아 렌더·부수 호출을 건너뛰면(직접호출 모드) 화면을 결제 단계로
  따라오게 할 수 있는가. 못 하면 좌석을 잡아도 사람이 결제를 못 한다.
