## 1. 달력 건너뛰고 조회 화면에서 시작  — 구현됨, 09:00 실전 미검증

### 처음 방법(주소로 뛰어들기)은 막혔다

조회 페이지 주소는 `/booking/select-award-flight/departure` 뿐이고 물음표 뒤가 비어
있다. 게다가 응답에 `jsessionId`(아마데우스 `aere-xml-controller`)와 `pageTicket` 이
있다. 페이지 티켓은 **흐름 순서를 강제하려고 존재하는 장치**다 - 중간 페이지로
뛰어드는 것을 막는 게 그 목적이다. 밖에서 주소로 들어가는 길은 닫혀 있다.

### 바꾼 방법: 그 화면에 서 있다가 그 자리에서 새로고침

이미 세션 안에 있으므로 티켓도 살아 있고 주소에 날짜가 없어도 상관없다. 그리고
조회 화면은 **자기 화면에 7일치 날짜 띠를 들고 있다**(`upsellCalendarFareList`,
선택일 ±3일). 어제 08-21 로 조회해두면 오늘 열리는 08-22 가 그 안에 있다.

달력 한 장과 그에 딸린 페이지 전환이 통째로 빠진다.

### 모드로 만들었다

체크박스 하나에 조용한 폴백이면 "어느 페이지에 서 있어야 하는지" 가 안 보인다.
패널의 **시작 화면** 을 달력/조회 화면 중에서 고르고, 지금 제대로 서 있는지를
초록/빨강으로 보여준다. 09:00 에 엉뚱한 화면에 서 있었다는 걸 그때 알면 늦다.

### 틀린 전제 하나 (2026-08-27 저녁)

"09:00 전에 조회 화면을 목표 날짜로 맞춰두면 된다" 고 봤는데 틀렸다. 새로 열리는
날짜는 09:00 에야 예약 가능 창에 들어오므로 08:59 에는 고를 수조차 없다.
그래서 화면의 달력에서 날짜를 바꾸는 과정이 반드시 필요하다.

### 실측으로 알아낸 화면 구조 (2026-08-27)

- 날짜칸: `kds-dateinput` / `[class*="ui-dateinput__host"]`. 라벨 "08월 21일 (토)".
  **감싸개(div.-dateinput)도 같이 잡히는데 그걸 누르면 달력이 안 열린다** -
  다른 후보를 품지 않은 가장 안쪽만 쓴다

  **예약 가능한 날에만 `-available`** 이 붙는다. 09:00 에 하루가 늘어난다

  날짜만 바꾸면 머리말만 바뀌고 목록은 그대로다 - 이걸 눌러야 다시 조회된다

### 안전장치 (엉뚱한 날 예매 방지)

주소에 날짜가 없으니 "지금 몇 일자를 조회 중인가" 를 따로 알아내야 한다. 근거가 둘이다:

- `KE_UTIL.searchedDate()` — 검색 위젯의 날짜 입력칸(`kds-dateinput`, 라벨 예:
  "08월 21일 (토)"). **좌석이 없어도 있다.** 09:00 직전 상황에서는 이것뿐이다
- `KE_PROBE.shownDate()` — 서버 응답의 `departureDate`. 좌석이 있을 때만 나온다

둘 다 있는데 서로 다르면 화면이 낡았다는 뜻이므로 건너뛰지 않는다. 아무것도 확인이
안 돼도 건너뛰지 않는다. 3초 벌자고 엉뚱한 날에 마일리지를 태울 값이 아니다.

## 2. 여러 계정 · 여러 노선 동시 시도

**하고 싶은 것**
- 두 계정(본인 + 배우자)으로 각각 시도
- 같은 계정으로 여러 노선 동시 시도

**구조상 문제**
- 계정은 쿠키 단위다. 같은 브라우저 프로필에서 두 계정 로그인은 불가능하다.
  → **크롬 프로필을 분리**하거나 시크릿 창을 쓰는 수밖에 없다.
- 재생 상태(`ke_award_steps_v1`)는 localStorage 라 **오리진 단위로 공유**된다.
  같은 프로필의 새 탭 두 개가 서로의 `idx` 를 덮어쓴다. 지금 구조로는 동시 실행이
  깨진다. 탭마다 다른 키를 쓰게 하거나(예: `sessionStorage` 로 이전), 아예
  프로필을 나눠야 한다.
- 한 계정 여러 노선도 같은 문제. 노선별로 상태가 분리돼야 한다.

**먼저 정할 것**: 프로필 분리로 갈지(간단·확실, 창이 여러 개), 한 프로필에서
탭별 상태 분리로 갈지(복잡, 계정은 여전히 하나). 계정이 둘이면 프로필 분리는 필수다.

**주의**: 같은 계정으로 동시에 여러 예매를 시도하면 사이트가 세션 충돌로 막을 수
있다. 소규모로 먼저 확인할 것.

## 4. 매일 같은 시각 자동 반복

되살릴 때 알아야 할 것:

- 구현 자체는 작다. `hud.js` 에 `repeatDaily` 플래그, 체크박스, 그리고 발사 시각을

- 진짜 문제는 **무인 운전의 전제 조건**이다. 브라우저·탭이 계속 열려 있어야 하고,
  로그인 세션이 밤새 살아 있어야 하고, 탭이 숨겨져 있으면 크롬이 타이머를 늦춘다
- 로그인 확인(`util.js` 의 `loggedOut()`)과 스로틀링 회피(`keepAwake()`)는 남겨뒀다.
  둘 다 매일 반복과 무관하게 무장해두고 자리를 비울 때 필요하다
- 사람이 화면 앞에 없는 채로 결제까지 가는 것이므로, 되살린다면 결제 단계를
  자동으로 둘지부터 물어야 한다

## 5. 프레스티지 '매진' 판정이 어디서 오는지 확인

사용자 관찰: 달력에서 검색하고 좌석 등급 화면으로 넘어가면 5초 만에 프레스티지가
이미 매진인 날이 있다.

5초 안에 결제까지 끝낸 사람이 있을 수는 없다. 남는 설명은 둘이다:

- **(가) 좌석을 고르고 넘어가는 순간 서버가 잠근다(hold).** 그러면 결승선은
  '결제하기' 가 아니라 '다음'(5단계, 실측 7.8초 지점)이고, 그 뒤 14.8초는 경쟁이
  아니다. 최적화 대상이 통째로 바뀐다 — 5단계까지만 죽어라 줄이면 된다
- **(나) 화면에 보인 잔여석이 캐시된 옛날 값이었다.** 그러면 지금처럼 빨리 가는 것
  말고는 할 게 없다

어느 쪽인지는 서버만 알지만, 화면이 잔여석을 그릴 때 쓰는 API 응답은 볼 수 있다.
`ke_award/probe.js` 가 조회 응답을 자동으로 기록한다(패널의 `조회 응답` 버튼).
09:00 에 한 번 돌린 뒤 그 기록을 보면:

- 잔여석 필드 이름과 값
- 우리가 '다음' 을 누르기 전후로 그 값이 달라지는지
- 매진으로 보였을 때 응답이 0을 주는지, 아니면 아예 목록에서 빠지는지

이게 확인되면 1번의 "API 직접 호출" 을 검토할지도 그때 정한다.

끊긴다.** 새 문서에서는 사람의 클릭 없이 소리를 다시 낼 수 없다(자동재생 정책).
그래서 정작 경쟁이 벌어지는 재생 구간이 무방비다.

- **지금은 알리기만 한다** — 가려진 채로 발사하면 소리와 알림으로 먼저 말하고,
  재생 중 가려지면 패널에 빨갛게 띄운다. 막지는 못해도 왜 느린지는 알게 된다

## 7. 직접호출 모드 — 렌더·부수 호출을 건너뛰어 3~5초 줄이기

09-02 실전에서 3초 차이로 졌다. 09-03 관찰(`dev/observe.py`)로 어디를 줄일 수 있는지
숫자가 나왔다: 단계별 총 시간 중 서버 몫이 검색 6% / 5.다음 62% / 7.확인 27% 이고,
나머지는 페이지 렌더와 **예약과 무관한 부수 호출**(회원정보·수하물정책·알림)이다.
브라우저 안에서 페이지가 자기 요청을 직접 쏘면(`probe.reAsk()` 와 같은 방식) 그 부분을
통째로 건너뛴다. **다만 좌석을 실제로 잡는 `inputTravellers` 는 서버에서만 4~6초라 못 줄인다.**
현실적 절감 3~5초.

**진행 전에 반드시 풀어야 할 것 (안 풀리면 이 항목은 접는다)**
요청만 쏘면 **화면이 안 따라온다.** 서버 상태만 앞서가고 브라우저는 그 자리에 있다.
그런데 결제는 사람이 해야 하므로 마지막엔 정상 결제 화면에 서 있어야 한다.
주소로 결제 페이지에 뛰어드는 길은 pageTicket 이 막는다(FACTS 참고).
→ **"요청을 쏜 뒤 화면을 결제 단계로 따라오게 할 수 있는가" 를 먼저 확인한다.**
일반석·계측 계정으로 위험 없이 확인 가능하다.

순서: 1) 화면 따라잡기 가능 여부 → 2) 가장 느린 한 단계만 교체 → 3) 일반석으로 검증.
예매 계정은 검증이 끝나기 전에는 건드리지 않는다.

## 9. 계측기 첫 측정이 늦다 — 오픈+7.95초 (승부는 10초 안에 난다)

09-04 13:28 리허설(차가운 크롬, CDG→ICN):

    발사 → 조회 화면 도달   오픈+4.64s (재고침 0회)
         → 첫 측정          오픈+7.95s
    이후 간격은 목표대로 1.0~1.3초, 23건

전에 잰 최고는 **오픈+2.30초**였다(09-03, 이미 열린 날짜 · 달궈진 크롬 · FCO).
5.6초 늦다. 좌석은 10초 안에 1→0 이 되므로 **이 상태로는 그 순간을 놓칠 수 있다.**
좌석이 몇 초에 0 이 되는지가 이 프로젝트가 재려는 유일한 숫자다.

**아직 원인을 모른다. 데이터가 두 점뿐이다.** 갈릴 만한 것:
차가운 크롬인가 / 노선(CDG vs FCO)인가 / 그냥 편차인가 /
'조회 화면 도달 4.64초' 자체가 느린 건가, 도달 후 첫 조회까지 3.3초가 문제인가.

**먼저 할 일**: 같은 조건에서 3~4번 재서 편차인지 본다. 편차가 아니면 4.64 / 3.3 중
어느 쪽이 큰지 나눠 잰다. 리허설을 돌릴 때마다 이 두 숫자를 남기면 공짜로 쌓인다.

## 10. 리허설이 2단계까지만 본다

`rehearse.py` 는 이미 열린 날짜로 쏜다. 그 날짜는 프레스티지가 늘 매진이라
매크로가 **3단계 이후로 갈 수가 없다.** 즉 리허설이 보증하는 것은
`차가운 시작 → 로그인 → 셋업 → 발사 → 조회 화면 도달` 까지다.
**결제까지 가는 길(3~17단계)은 리허설이 보지 않는다.**

09-04 사고가 그 앞구간이라 지금은 이게 맞는 우선순위다. 하지만 "리허설 통과"를
"다 된다"로 읽으면 안 된다. 3단계 이후는 08-30 에 두 노선 17/17 완주로 확인한 것이
마지막이다(FACTS 참고).

**생각해 볼 것**: 일반석은 좌석이 남아 있다(리허설마다 "일반석 9"). 일반석으로
`--dry` 발사하면 3단계 이후도 밟아볼 수 있다. 주문은 7단계 앞에서 멈추니 안 생긴다.
