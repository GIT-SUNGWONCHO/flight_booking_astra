> PC 와 같다. **모바일 화면폭에서는 화면만 갈라질 뿐이다.**

> **2026-09-23 정정.** 최초 판의 **"모바일 줄기는 닫혔다"**는 **철회한다.** 이 실험이 닫은 것은
> "모바일 *레이아웃*에 좌석을 먼저 잡는 추가 호출이 있다"는 가설뿐이다.
> **네이티브 앱은 이 실험의 대상이 아니었다**(§7.4).

## 8.2 같은 계정 동시 로그인 — 서로 끊지 않는다

본인 계정으로 9233·9242 두 브라우저에 동시 로그인하고 8회 번갈아 조회했다.
**양쪽 4/4 성공**(1,551~1,960ms), 회원 세션은 끝까지 유지됐다.

## 8.3 2계정 동시 예매 리허설 — 성공 (23:00)

이미 열린 2026-12-17 일반석(5석)에서 9232(와이프)·9242(본인)가 같은 시각에 발사했다.

| | 9232 와이프 | 9242 본인 |
|---|---|---|
| 발사 | 23:00:01.095 | 23:00:01.093 |
| 조회 | **1,714ms** | **2,852ms** |
| 운임 | 1,536ms | 1,438ms |
| 주문 송신(fetch 시작) | +3.300초 | +4.329초 |
| 주문 응답 | 6,902ms | 6,712ms |
| 예약번호 | **발급** | **발급** |

**좌석 5 → 3.** 두 계정이 각자 한 석씩 가져갔다. 전송권은 상태 폴더를 나누면 서로 막지 않는다
(`state-reh-a`·`state-reh-b`). 두 건 모두 미결제로 자동 해제 대상이다.

판정은 `amount-mismatch` 로 남았는데, 운임 `amount=0`·주문 `amount=totalAmount` 라는
**기존에 알려진 응답 형태**(FACTS §1) 때문이다. `totalAmount`·마일리지는 일치했고 예약은 생성됐다.

> **부작용**: 동시에 보낸 두 조회 중 하나가 **2,852ms** 로 평소(1.4~1.8초)보다 1.1초 느렸다.
> 같은 PC 에서 동시 실행이 한쪽을 밀어낼 수 있다. 표본 1개이므로 실전에서 재확인한다.
