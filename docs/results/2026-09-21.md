## 4. Δ와 [조건부] 주문 시각 역산

**Δ(실전 부하) = 우리 좌석 감소 경계 − 우리 주문 송신 = (3.754, 3.902] − 2.408 = +1.35 ~ +1.49초**

### Δ가 정확히 무엇인가

주문 시작을 O, 주문→재고 반영까지를 H, 관측 조회 시작을 Q, 조회 시작→재고 판독까지를 L이라 하면
경계에서 `Q + L ≈ O + H` 이므로 **Δ = Q − O ≈ H − L** 이다.

- Δ는 **순수한 주문 처리 시간(H)이 아니다.** L을 모르는 한 H를 복원할 수 없고,
  조회 RTT 전체를 더해 H를 만드는 것도 틀리다.
- 9/21 오후 통제 실험(§9.4)에서 주문 시각은 **Playwright `request` 이벤트 콜백 안의
  `time.time()`**으로 찍었다. 정확히는 *주문 요청 이벤트를 관측한 시각*이며 브라우저가 기록한
  네트워크 시작 시각이 아니다. 이 차이를 검증할 다른 시각은 남기지 않았다.
- 같은 조건에서 보정값으로 쓰는 것은 가능하지만, **다른 요청·부하·날짜·주체에도 같다는 근거는 없다.**
  Δ를 보편 상수처럼 쓰는 것이 이 문서들이 반복해서 빠진 함정이었다.

**보내는 것의 96%가 쿠키**이고 본문은 54~405바이트다. 네트워크 왕복이 30ms 이므로
크기를 줄여 얻을 수 있는 것은 1ms 수준이다. **요청 크기는 병목이 아니다.**

달력에서 60초 대기 중 나간 요청은 **1건**(`/api/li/auth/refresh`). 상시 폴링은 없다.
다만 이 갱신이 발사 구간과 겹치면 같은 세션 요청이 밀릴 수 있다.

미확인: 재전송은 캡처 시점의 `timestamp`·`x-dtpc` 헤더를 그대로 보낸다.

### 9.4 δ 비교 — 사이트 자체 주문과 우리 재전송

같은 날짜(2026-12-17 일반석)에서 5분 간격으로 짝지어 측정. 계측 0.15초 간격.
**각 모드 주문 1회씩, 총 2회의 시행이다.**

| 주문을 보낸 주체 | 좌석 변화 | 주문 송신 → 좌석 감소 (송신 축) |
|---|---|---|
| **사이트 화면 자신** (17:03) | 4 → 3 | **+1.413 ~ +1.566초** |
| **우리 API 재전송** (17:08) | 3 → 2 | **+1.356 ~ +1.509초** |

구간이 +1.413~1.509에서 겹친다. 중심값 차이는 약 56ms로 표본 경계 폭(153ms)보다 작다.
9/20 야간 우리 API +1.56~1.71, 9/21 09:00 우리 API +1.35~1.49 도 인접한 구간이다.

→ **이 두 시행에서는 재전송 모드만의 큰 추가 지연이 관측되지 않았다.**

**측정 한계(2026-09-23 검토)**

- **`samples=120`은 조회 응답 수이지 주문 시행 120회가 아니다.** 주문은 각 1회다.
- **153ms 구간 폭은 감시 조회의 송신 간격**이지 실제 재고 변경 시각의 신뢰구간이 아니다.
  유의성 검정이나 동등성 검정은 하지 않았다.
- **전이 구간의 표본 행이 남아 있지 않다.** 스크립트가 표본별 행을 표준출력으로만 찍었고
  파일로 저장한 것은 `changes` 요약뿐이다(`research/delta-{site,api}-20260921-*.json`).
  터미널 기록에 남은 꼬리는 사이트 id 69~119, API id 94~119로 **전이가 끝난 뒤 구간**이다.
  따라서 **두 요약값을 독립적으로 재계산할 수 없다.**
- 주문 시각은 Playwright `request` 이벤트 콜백의 `time.time()`이다(§4의 Δ 정의 참조).
- 통제 스크립트는 120개 타이머 요청에 동시 상한이 없지만 운영 계측기는 동시 상한 12를 쓴다.
  관측 조건이 09시 실전과 같지 않다.

> **2026-09-23 정정.** 최초 판의 **"상태 인계·페이지 안 재전송·캡처 본문·발사 시점 화면은 원인이
> 아니다"**와, 이 결과를 근거로 다른 문서에 쓴 **"웹으로 보내는 주문은 누구 것이든 같다"**는
> **철회한다.** 시행 2회에서 큰 차이가 안 보였다는 것까지가 관측이고, 모든 계정·경로·시각에서의
> 동등성은 입증되지 않았다.

## 10. [조건부] 격차 — 가정 위에 선 계산이다

**Δ 가 누구에게나 1.35~1.71초이고, 각 감소의 원인이 외부 주문일 때** 역산은 이렇게 된다(§4와 같은 값).

| 날짜 | 좌석 감소 경계(송신 축) | − Δ | [조건부] 주문 송신 |
|---|---|---|---|
| 9/21 | +2.101 ~ 2.254 | 1.35~1.71 | +0.39 ~ +0.90초 |
| 9/20 | +2.303 ~ 2.902 | 1.35~1.71 | +0.59 ~ +1.55초 |

조회→운임→주문의 **경험적 기준**은 +1.85초다(−0.95초 발사 + 조회 최속 1.40 + 운임 최속 1.40).
이는 관측된 최솟값의 합이며 물리적 하한이 아니다.

> **2026-09-23 정정.** 최초 판의 **"첫 번째 좌석 감소는 우리가 쓰는 웹 경로로 만들 수 없다"**는
> **철회한다.** 이 문장은 ① Δ의 보편성, ② 감소 원인이 주문임, ③ 송신 경계 = 실제 재고 변경 시각,
> ④ +1.85초가 물리적 하한임 — 네 가지 가정을 동시에 요구한다. **넷 다 확인되지 않았고,
> ③은 [9/23 §3.1](2026-09-23.md)에서 실제로 반례가 나왔다.**

남는 설명은 여러 갈래이며 **어느 것도 지지·기각되지 않았다.**

- **A** 더 빠른 입구가 있다 — 웹에서 볼 수 있는 범위는 찾아봤고 못 찾았다([9/22 §7](2026-09-22.md)).
  네이티브 앱은 미조사.
- **B** 항공사 쪽 재고 처리(정리·재검증·채널 간 이관)
- **C** 실제 경쟁 예약 — **여전히 가장 단순한 설명이다**
- **D** 가정 자체가 틀렸다 — 실제 재고 변경 시각이 관측 구간보다 훨씬 뒤일 수 있다

최초 판이 제안한 "좌석 9석짜리 날을 계측하면 A/B가 갈린다"는 **성립하지 않는다.**
`seatCount`가 9에서 상한에 걸려 감소 자체가 보이지 않기 때문이다([9/23 §6.4](2026-09-23.md)).
또 계단형 감소가 관측돼도 그것만으로 A와 B를 가를 수 없다([9/22 §4](2026-09-22.md) 주석).
