# 검증 검토 지침

## 1. 목적과 적용 시점

시험 결과의 과대 해석을 막는 검토 절차다. 권한은 [AGENTS](../../../AGENTS.md), 시험 기준은 [docs/testing.md](../../../docs/testing.md)가
원본이다. 실행 변경과 리허설·09시 결과 보고 전에 적용한다.

## 2. 시험 범위 분류

| 분류 | 필수 구분 |
|---|---|
| T1 로컬 | 픽스처·유닛·로컬 Chromium. 실사이트 성공 아님 |
| T2 리허설 | 실사이트·이미 열린 날짜. 노선·날짜·등급·시각·환경·도착 범위 명시(`--dry`·워밍·콜드 스타트 구분) |
| T3 실조건 | 실제 09:00 신규 개방을 동일 실행 로그로 확인. 연속 2회 전에는 `1/2`로 보고 |

## 3. 결과 보고 전 점검

1. 이미 열린 날짜인지 신규 개방인지, 일반석인지 프레스티지인지 확인한다.
2. 노선·편·출발일·캡처 날짜·KRW·선발사·시계 오프셋·불확실성을 실제 로그와 대조한다.
3. 기동 방식(작업 스케줄러·수동), Chrome 재시작과 OS 부팅, 로그인 상태 차이를 적는다.
4. 동일 실행의 `api_day` 보고서·`fire-timing`·주문 증거·계측 로그를 읽는다. 서로 다른 실행 ID를 섞지 않는다.
5. 방향별 도착 범위: ICN 출발 = Npay 결제창(`npay-checkout`), ICN 도착 = 결제수단 직전 정지(`user-payment-method`). 로그인·오류·이전 창은 통과가 아니다.
6. 계측은 유효 응답·미개방·오류·건너뜀·처음부터 P 없음을 구분한다. P 있음·없음 표본이 모두 있을 때만 관측 구간을 말한다.
7. 주문 실패는 오류 코드·예약번호 유무·전송권 상태를 함께 보고한다.

## 4. 변경 후 시험 선택

[docs/testing.md §3](../../../docs/testing.md)의 변경별 시험을 적용한다. API 변경은 `api_booking/run_tests.py` 전체와
`--dry` 경로 점검. Chrome을 이름으로 일괄 종료하지 않는다. 문서만 바꿨으면 링크·명령·코드/설정 대조로 검사한다.

## 5. 보고 형식

**시험 범위 → 실제 수치·도착 증거 → 실전과 다른 조건 → 남은 확인** 순서. 예: "콜드 스타트 통과 — 이미 열린 일반석,
작업 스케줄러 기동, 주문 송신 +2.79초, 결제수단 직전 정지. 09시 신규 프레스티지는 미검증." 로그를 읽지 않고 통과라고 말하지 않는다.
