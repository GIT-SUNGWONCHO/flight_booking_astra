# 검증 검토 지침

## 1. 목적과 적용 시점

이 지침은 시험 결과의 과대 해석을 막는 검토 절차다. 작업 권한은 [AGENTS](../../../AGENTS.md), 동작·완료 기준은 [README](../../../README.md#validation)가 원본이다. 실행 변경과 준비·리허설·09시 결과 보고 전에 적용한다.

## 2. 시험 범위 분류

| 분류 | 필수 구분 |
|---|---|
| T1 로컬 | 픽스처·유닛·프로세스 시험. 실사이트 성공 아님 |
| T2 리허설 | 실사이트의 노선·날짜·등급·시각·환경과 실제 도착 범위를 명시 |
| T3 실조건 | 확정 일정의 실제09시 신규 개방을 동일 실행의 로그로 확인. 연속2회 전에는 `1/2`로 보고 |

실전 예매는 사용자 대기 후 패널이 정시에 시작하는 현재 명세를 기준으로 본다. 시험을 위해 사용자를 대신해 실전 대기를 걸거나 다른 발사 경로를 만들지 않는다.

## 3. 결과 보고 전 점검

1. 이미 열린 날짜인지 신규 개방인지, 일반석인지 프레스티지 경쟁인지 확인한다.
2. 확정 노선·출발일·KRW·선발사·진입점·사용자 대기 상태와 실제 설정을 대조한다.
3. 브라우저 실행 방법·프로필·배경 상태·로그인·네트워크 환경의 차이를 적는다. Chrome 재시작과 OS 부팅을 구분한다.
4. 동일 실행의 보고서·해시·시각·작업자 상태를 읽는다. 예매·계측의 서로 다른 자식 실행 ID를 부모 기록으로 연결한다.
5. 예매는 방향별 목표와 provider·stage를 대조한다. ICN 출발=Npay, ICN 도착=현대카드 인증수단 선택창. 로그인/오류/이전 실행의 창은 통과가 아니다.
6. 계측은 유효 응답·미개방·오류·누락·처음부터P없음을 구분한다. P 있음과 없음 표본을 모두 얻었을 때만 관측 구간을 보고한다.

## 4. 변경 후 시험 선택

신규 개방 의존 코드는 미개방→P있음→P없음 전이 픽스처를 먼저 통과시킨다. 실행 변경에는 [README의 변경별 시험표](../../../README.md#handoff)를 적용한다. 핵심8개와 변경 관련 시험을 수행하되 Chrome 이름으로 일괄 종료하지 않는다.

알려진 실행 결함은 수정하거나 적용을 보류하고 [NOW의 미완료 항목](../../../NOW.md)에 번호와 다음 확인 조건을 남긴다. 문서만 변경했으면 파일 링크·명령 문법·코드/설정 대조로 검사한다.

## 5. 보고 형식

**시험 범위 → 실제 수치·도착 증거 → 실전과 다른 조건 → 남은 확인** 순서로 쓴다. 예: ‘리허설 통과 — 이미 열린 일반석에서 실제 Npay 도착. 실제09시 신규 프레스티지는 미검증.’ 실행 로그를 읽지 않은 채 통과했다고 말하지 않는다.
