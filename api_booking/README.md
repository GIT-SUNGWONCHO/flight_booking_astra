# API 예매 개발 계획 — 클로드 실행 원본

기준: 2026-09-13 사용자 재확정. **이 문서 §3은 전체 처리 순서, §4는 개발 순서, §5는 시험 통과 조건이다.** 현재 첫 작업은 [NOW](../NOW.md), 시작 프롬프트는 [§8](#claude-prompt). 과거 A1~A8 기록의 ‘다음 작업’은 적용하지 않는다.

## 1. 목표와 완료의 의미

- 시작: 정상 로그인된 브라우저의 **달력 화면에서 목표 예매를 시작할 수 있게 준비**한다. 어제 주문/결제 게이트에 머물러야만 API가 동작하는 구조는 완료가 아니다.
- 성능: 개방 기준 T0부터 목표 주문의 임시 보유까지 단축. 주문 전송 ≤3초는 도전 목표이며, 사용자에게 6~7초 확보도 의미가 있다. 둘은 다른 지표다.
- 기능: API 조회·운임·필수 검증·주문 후 **같은 주문**의 브라우저 동의·마일리지 적용·Npay 선택·실제 Npay 창까지 연결한다. 최종 승인은 사용자만 한다.
- 브라우저는 처음부터 살아 있다. 1회 인계는 중간 화면의 렌더링/클릭 대기를 줄인다는 뜻이며, 페이지별 클릭 재생을 모두 강제하거나 정상 상태 갱신을 생략한다는 뜻이 아니다.
- 사용자 설명에 따라 pnr의 임시 보유 의미를 반영한다. 다만 전송 시각·pnr 응답 시각·실제 서버 보유 시작 시각·해제 시각은 구분한다. 정확한 시작/기한은 미확인이다.
- 일반석 가상 T0와 실제 09시를 구분한다. 5초 매진 마감·9.4초 구조적 하한·주문 왕복 전부가 단축 불가능한 서버 처리라는 주장은 사용하지 않는다. 운영 시계는 수정하지 않는다.

## 3. 전체 API 예매 프로세스 — 순서 유지

| 순서 | 처리 | 통과 조건 |
|---|---|---|
| 1 | 브라우저 사전 준비 | 본인 정상 로그인·KRW·승객/연락처·목표·세션. 달력 상태에서 실행 가능. 준비 중 주문 여부를 별도 식별 |
| 2 | 사용자 대기 시작 | 목표/설정/코드/세션 확인. 변경 시 준비 무효화. 지나간 발사 시각은 자동 실행 금지 |
| 3 | awardAvailability | 개방 후 목표 전체 날짜·출발지·도착지로 조회. 미개방/오류/매진 구분 |
| 4 | 목표 선택 | 날짜·노선·운항사·편명·등급·재고 검증. 같은 최신 응답의 recommendId/flightId 선택 |
| 5 | fareInformation | 최신 식별자로 운임 요청. 여정·등급·KRW·금액·필요 마일리지·pageTicket/세션 문맥 검증 |
| 6 | 필수 회원·마일리지·세션 검증 | 재사용 가능한 사전 증거만 사용. 새 필요액과 실제 가용 잔액 비교, 승객·연락처·회원 적격 확인 |
| 7 | inputTravellers 1회 | 최신 운임 문맥 일치, 검증 완료, 전송권 획득과 의도 기록 이후 전송 |
| 8 | 동일 주문 상태 확인 | pnr뿐 아니라 목표 여정·등급·업무 상태 대조. 응답 불명확은 ORDER_UNKNOWN, 재전송 금지 |
| 9 | 브라우저 1회 인계 | 현재 API 주문과 화면 주문 식별자 연결. 검색/운임/승객/금액 상태 일관성, 새 주문 생성 없음 |
| 10 | 동의·마일리지·결제수단·결제창 | 기존 브라우저 방식. 각 동의 완료, 실제 마일리지 적용, Npay 선택, 새 실제 제공자 창 확인 |
| 11 | 최종 결제 승인 | 사용자만 수행 |

같은 로그인 Chrome의 정상 요청 문맥을 사용한다. 인증·접근 대기·필수 검증을 생략하지 않는다. 최신 조회에 의존하는 운임을 추측으로 병행하지 않고 과거 식별자로 대체하지 않는다. 정상 인계에 필요한 **같은 주문 읽기**는 허용하며 별도 계측한다. 주문 재생성은 인계 방법이 아니다.

## 4. 개발 보완 순서 — 한 번에 한 가지

D1~D5는 새로 합의한 보완 작업명이다. A1~A8을 처음부터 다시 만드는 계획이 아니다. D1의 계약 조사·로컬 모델은 선행 가능하지만 **실제 주문 시험은 D3/D4까지 갖춘 뒤 §5에서만** 수행한다.

| 단계 | 구현 범위 | 로컬 완료 조건 |
|---|---|---|
| **D1 첫 작업: 동일 주문 인계 계약** | 사이트 정상 주문 응답 처리/store/action/라우팅 또는 정상 같은 주문 재개 경로 조사. 기존 handoff/site_drive에 최소 연결 모델 추가 | 새 주문과 이전 주문 구분. 같은 날짜·마일리지라도 다른 pnr은 거부. 새 주문 요청을 유발하는 인계는 실패 |
| D2 달력 시작 준비 | 페이지 수명과 요청 문맥 보존을 정리하고 달력에서 API 시작 가능하게 연결 | 달력 복원/문서 전환 뒤 필요한 문맥 유지 또는 명확한 재준비. 주문 페이지 고정 의존성 제거. 준비/조회/주문 구간 호출 수 구분 |
| D3 실제 계약과 검증 연결 | 기존 A2~A4와 실전송 경로의 입력·응답 차이를 대조하고 필요한 판정을 연결 | 잘못된 날짜/노선/편명/등급, 매진/미개방/업무 오류, 잔액 부족/세션 만료에서 주문0회 |
| D4 주문 전송 안전성 | 실제 전송 직전 배타 전송권·의도 기록·불명확 복구·늦은 무장 차단 | 두 프로세스 동시 시작 중 하나만 전송. 중단/응답 유실/재시작 후 새 주문 차단. Windows 시험 |
| D5 브라우저 후반 연결 | 동의→마일리지→Npay 선택→실제 Npay 판정을 기존 정상 단계와 연결 | 체크된 동의를 다시 꺼버리지 않음. 실패 전파. 카드 PG·로그인·이전 창·금액 불일치는 완료 아님 |

### D1에서 바로 할 일

1. `transport.py`, `live_order.py`, `site_drive.py`, `handoff.py`와 9/13 최종 검토를 대조한다. 기존 판정 모델을 재구현하지 않는다.
2. 보존된 사이트 소스/수집에서 주문 응답→정상 화면 상태→게이트의 연결 위치를 찾는다. 파일·함수·필드·호출 순서·페이지 이동 부작용을 기록한다. 자료가 없으면 없는 항목을 명시한다.
3. 우선은 정상 상태 갱신을 유지하고 화면을 인계하는 경로, 다음 후보는 정상 같은 주문 조회/재개 경로다. 단순 `goto(GATE)`·성공 플래그 주입은 확정 경로가 아니다.
4. `Order.reference`와 실제 화면이 사용하는 주문 참조를 메모리에서 비교할 방법을 계약으로 정한다. 날짜·마일리지·KRW 일치만으로 대체하지 않는다. 식별자 원문은 로그에 쓰지 않는다.
5. 확인된 계약만 최소 구현·가짜 브라우저/전송기로 시험한다. 실제 계약이 부족하면 합성을 실증으로 승격하지 말고 **다음에 수집할 한 가지 증거**를 특정해 남긴다.

### 개발 중 빠뜨리면 안 되는 항목

- **회원/선택 문맥:** inputTravellers 본문에 여정이 없다는 것만으로 전달 메커니즘을 확정하지 않는다. fare 결과·pageTicket·쿠키/헤더·서버 선택이 목표와 이어짐을 확인한다. 다른 탭/작업의 선택 변경도 고려한다.
- **계약 차이:** 현재 travellers 합성 모델은 연락처1항목, 실측은 contactList2항목. 실제 허용 구조로 보완한다. 캡처 일반석/이전 날짜→새 날짜 프레스티지 조합·travellerId 수명·본인 잔액을 검증한다.
- **사전 처리:** 가족정보/회원검증을 속도 때문에 무조건 생략하지 않는다. 캐시의 입력 키·유효 조건·강제 갱신·여정 의존성을 확인한다. 현재 본인 예매 범위를 가족 합산으로 임의 확장하지 않는다.
- **준비 부작용:** capture_pass/replay_probe는 캡처만으로 임시 주문을 만들 수 있다. live_order의 `--dry`도 캡처까지 무주문으로 보장하지 않는다. 주문 없는 준비 방법을 우선 조사하고, 불가하면 생성 건수/상태를 명시해 시험 범위를 구분한다.
- **페이지 수명:** add_init_script 등록, 현재 문서의 캡처, 브라우저 연결 재생성은 다른 상태다. 단순 complete/존재/캡처 나이를 로그인 유효성이나 화면 준비 완료로 해석하지 않는다. 헤더 timestamp의 보편적 유효기간을 30분 표본 하나로 정하지 않는다.
- **오류:** HTTP200/JSON/pnr 존재/exit0만으로 성공 금지. 전송 후 응답 불명확·잘못된 여정·업무 오류는 서버 주문 부재를 뜻하지 않는다. 정상 조회에서 안 보인다는 사실만으로 재전송 허용 금지.
- **후반 UI:** 동의는 두 모달 각각 상태·스크롤·완료를 확인한다. Npay가 안 되면 다른 PG로 대체하지 않는다. 마일리지 적용액·최종 KRW 금액·현재 주문을 대조한다.
- **현재 금지:** `--continue-payment`는 결함 수정·관련 검증 전 사용 금지. `--gate-only`는 동일 주문 보장 없음. 로컬 intent의 resolved는 서버 해제 증거가 아니다. 재실행을 위해 파일을 임의 삭제하지 않는다.
- **범위:** 연구 기본9242, 과거9232 예외는 AGENTS 참조. 운영9232/계측9233·시계·사용자 대기·일정 자동 변경 금지. 계측 실패가 예매를 중단시키지 않는다.

| T2b 일반석 전체 | 달력 준비→사용자 시험 시작→API 주문1회→같은 주문 인계→실제 Npay | D1~D5 기능 연결, 준비 포함 실제 주문 건수 기록, 인계 후 재주문0회, 최종 승인 없음 |
| T2c 최종 후보 | 회사 Windows 동일 후보로 전체 흐름 연속2회, 세션 재준비 포함 | 실행/코드 해시 일치, 실패 포함 개별 성능, 이전 시험 주문 상태 확인. 조건/코드 변경 시 영향 구간 재검증 |
| T3 09시 실전 | 준비 조건·미검증·속도를 보고한 뒤 사용자가 적용·대기 결정 | 실제 신규 개방 여부와 결과 기록. 직전 미검증 변경/즉석 경로 교체 없음. T2 성공을 경쟁 성공으로 표현하지 않음 |

실사이트 요청·주문은 해당 시험이 명시적으로 허용된 범위에서만 한다. 일반석 반복 시험 전에 이전 주문 상태를 확인하며, 해제/복구 확인이 불가능하면 이를 숨기지 않고 후속 실제 주문 시험을 보류해 사용자에게 상황을 보고한다. 영구적으로 보유 시작 시각을 못 알아도 응답 확인과 정확한 시작 시각을 분리해 평가할 수 있다.

- 미개방 재조회는 조회만 허용된 횟수/간격/종료시각 안에서 수행한다. 밀린 요청 몰아 보내기 금지. 매진은 중단하고 다른 등급/날짜로 대체하지 않는다.
- 401/403·추가 인증·대기열은 정상 접근 절차로 처리, 429는 서버 대기 지침 준수. 오류를 재고 없음으로 분류하지 않는다.
- ICN 출발 성공은 현재 주문에 연결된 새 `pay.naver.com`/`m.pay.naver.com`의 실제 Npay 화면이다. 로그인·카드 PG·기존 창은 제외한다. 자세한 판정은 [상위 README](../README.md#validation).
- API 후반 단계가 실패하면 실패로 종료하고 **같은 주문 상태와 복구 필요**를 보고한다. 자동으로 UI 전체를 다시 돌려 주문을 만들지 않는다.

<a id="measurement"></a>
## 6. 성능·준비 완료 보고 계약

실행 ID·환경·목표·계정 익명 문맥·설정/실행 코드 해시와 다음 사건을 같은 실행에서 연결한다. 단조시계 경과시간과 절대시각 기준을 구분하며 Date 헤더를 재고 시각으로 사용하지 않는다.

| 지표 | 의미 |
|---|---|
| T0→조회 전송 | 시작 지연. 가상/예정/실제 개방 확인 구분 |
| 각 API 전송→첫 응답→본문→판정 | 실제 왕복·판정 비용. 순수 서버 처리라고 부르지 않음 |
| 응답 판정→다음 요청 | 제거할 수 있는 화면·로컬 대기와 필수 검증 비용 |
| T0→주문 전송 / pnr 응답 | 각각 기록. 실제 보유 시작 시각은 근거 없으면 미확인 |
| 인계 시작→동일 주문 확인→Npay | 후반 기능/비용. 주문 재전송·조회 횟수도 기록 |
| 실패·중단·준비 주문·해제 | 성공 표본만 남기지 않음. 해제 미확인은 그대로 표시 |

**준비 완료**는 목표·본인 계정/잔액·정상 세션·달력 시작 가능·검증된 전체 후보 코드·미해결 주문 처리·사용자 대기 조건을 확인한 범위로 보고한다. 캡처 complete나 과거120개 시험으로 대신하지 않는다. 정확한 서버 보유 시각/경쟁 성공은 별도 미확인일 수 있다.

## 7. 한 단계 종료와 기록

- NOW에는 완료 범위·현재 첫 작업 하나만 갱신한다. 이 문서 §4에는 단계 상태/계약을 반영한다.
- 길어지는 실행별 기록은 `docs/archive/<날짜>/`에 남긴다. 구현/시험 파일·실행 명령·환경·종료 코드·통과/실패·해시·미확인·정확한 다음 작업을 포함한다.
- 관련 로컬 시험은 `python api_booking/test_<대상>.py`를 개별 실행한다. Windows는 `.\.venv\Scripts\python.exe`, Mac은 `./.venv/bin/python`. 실제 존재하는 시험명을 선택한다.
- 실행 코드 변경의 교차 검토는 [ke-review](../.claude/skills/ke-review/SKILL.md)를 따른다. 정적 검토를 실사이트 검증으로 세지 않는다.
- 문서화 여유를 남겨 한 단계를 시험 가능한 상태로 마감한다. 담당 전환 시점은 사용자가 결정한다.
