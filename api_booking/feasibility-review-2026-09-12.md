# API 예매 계획의 목표 적합성과 구현 가능성 검토

검토일: 2026-09-12. 대상: 현재 작업 폴더의 설계·수집/분석 코드·보존된 실행 기록. 사용자 요청에 따라 검토 보고서만 작성했다. 실행 코드·시계·운영 설정은 수정하지 않았으며 사이트 예매·로그인·주문 시험은 수행하지 않았다.

## 1. 판정

**API로 중간 화면 대기를 제거하는 방향은 목표에 적합하다. 조회→운임→필수 검증→inputTravellers→동일 주문의 화면 인계는 연구할 가치가 있는 구조다. 그러나 현재 자료로 독립 실행 가능성, 해당 경계에서의 좌석 확보, 5초 이내 확보를 입증하지 못했다. 실전 적용 준비가 끝난 계획으로는 판정할 수 없다.**

| 검토 항목 | 판정 | 이유 |
|---|---|---|
| 목표와 방향 | 적합 | 개방 후 새 조회·운임·주문으로 이어지는 경로에서 달력·클릭·렌더링 대기를 줄이는 접근 |
| 정확히 API 3개로 충분한가 | 미확정 | 인증 처리, pageTicket, 회원 검증, 마일리지 검증 등 실제 의존관계가 남아 있음 |
| inputTravellers에서 좌석이 확보되는가 | 우선 조사 후보 | 예약번호와 구간 상태에 관한 근거가 있으나 정확한 보유 단계·시점·기한 미확인 |
| 주문 뒤 브라우저 1회 인계 | 조건부로 타당 | 정상 화면 모델·라우팅·토큰·주문 상태의 연결 방법을 아직 입증하지 못함 |
| 4.5초 전송 / 6초 마감 / 1.5초 여유 | 근거로 채택 불가 | 추정 왕복과 전송 시각을 사용했고 마감 도출에 논리·구간 계산 오류가 있음 |
| 개발 재개 | 검증을 위한 개발은 타당 | 실행기 완성보다 실제 요청 계약과 인계 경계를 먼저 입증해야 함 |
| Windows 실전 투입 | 아직 판단 불가 | Windows 독립 API 전체 리허설과 실제 개방 조건의 자료가 없음 |

이전 답변의 “7번에서 좌석만 잡으면 뒤는 시간에 쫓기지 않는다”, “5초가 아니라 6~7.2초 매진”, “0.132초 늦었다”, “현재 구조로 3초는 불가능”은 입증 범위를 넘었다. 아래 이유로 해당 결론을 철회하는 것이 맞다.

## 3. 처리 구조는 타당한가

추천하는 연구 구조는 다음과 같다. 여기서 API는 정상 로그인된 연구 Chrome의 같은 세션에서 수행하는 요청을 뜻한다. 브라우저를 없애거나 외부 Python HTTP 클라이언트로 즉시 이전한다는 뜻이 아니다.

```text
개방 전: 정상 로그인·KRW·승객 초안·재사용 가능한 검증 준비
  ↓
개방 후: 최신 항공편 조회 → 목표 편명/등급 선택 → 최신 운임
  ↓
해당 여정에 필요한 회원·잔액·세션 검증
  ↓
inputTravellers 1회 → 업무 응답·동일 여정/등급/주문 확인
  ↓
정상 화면 모델로 인계 → 동의·마일리지·결제수단 → 실제 결제창
```

화면을 표시하지 않으면서 정상 요청과 상태 전이를 수행한다는 방향에는 구조적 모순이 없다. 다만 “1~7단계가 정확히 HTTP 3회가 된다”는 약속은 아직 할 수 없다. 최신 조회 응답이 운임 입력을 공급한다는 문서상 연결은 직렬 의존성을 지지한다. 필수 검증은 별도 노드이며 사전 실행이나 병행 가능성은 입력·세션 의존성으로 결정해야 한다.

**항공편 ID가 inputTravellers 본문에 없다는 사실만으로 서버 세션이 모든 선택을 기억한다고 확정할 수 없다.** pageTicket, 헤더, 쿠키, 공통 요청 변환기, 추가 선행 호출이 문맥을 전달할 수도 있다. 이 가정이 틀렸다고 API 연속 처리 전체가 불가능해지는 것도 아니다. 실제 전달 경로를 확인해 재현할 수 있으면 연속 처리는 여전히 가능하다. 재현할 수 없는 필수 상태 전이가 발견됐을 때 해당 경계를 재검토해야 한다.

브라우저 인계는 “결과를 화면에 뿌리기”보다 큰 작업이다. 최소한 검색 조건·선택 운임·승객·연락처·주문 응답·화면 단계·pageTicket/세션의 일관성이 필요하다. 기존 문서도 운임 응답의 store 저장, ERETAIL 설정, 상태 초기화 후 라우팅을 명시한다. URL 이동 또는 예약 완료 플래그 하나로 대체하면 안 된다.

기존 8~17단계 클릭을 재사용할 수는 있다. 그러나 정상 UI 전체 흐름으로 도착한 화면과 API 주문을 주입한 화면은 진입 조건이 다르다. 기존 리허설 성공은 새 인계의 성공 증거가 아니다. 주문을 다시 만들지 않으면서 같은 주문의 정상 읽기 요청이 필요하다면, 그 비용을 허용하고 측정하는 것이 “추가 요청 0회”를 고집하는 것보다 목표에 맞다.

## 4. 좌석 확보 단계는 어디인가

**현재 판정 가능한 것은 inputTravellers가 가장 유력한 조사 후보라는 점이다. 정확한 확보 단계와 확보 시각은 미확인이다.**

문서에는 응답 pnr가 NaverPay의 reservationRecLoc으로 이어지고 사이트가 isPNRConfirmed를 설정한다고 기록돼 있다. HK 구간 상태도 기록돼 있다. 이는 예약과 연관된 업무 상태가 만들어질 가능성을 지지한다. 그러나 다음을 한꺼번에 입증하지 않는다.

1. 해당 요청이 처음으로 좌석을 점유한다는 것.
2. 전송 즉시 또는 서버 도착 즉시 점유된다는 것.
3. 목표 편명·등급·승객의 확정 보유이며 뒤의 마일리지/결제 단계에서 재검증하지 않는다는 것.
4. 보유 기한이 충분하고 화면 인계 실패 중에도 계속 유지된다는 것.

조회·운임에서 임시 상태가 만들어지거나 inputTravellers 처리 중 어느 시점에 보유될 수도 있다. 후반 단계가 추가 검증·만료 처리를 할 수도 있다. 이 중 어느 설명이 맞는지 현재 자료만으로 선택하지 않는다. HK의 이 시스템 내 업무 의미도 원본 상태 조회와 대조해야 한다.

중요한 직접 실측: 9/12 일반석 리허설에서 inputTravellers의 첫 응답은 요청 시작 후 **6.216초**, 본문 완료는 **6.219초**였다. 이 시간 전체가 좌석 확보까지 걸렸다는 뜻은 아니다. 반대로 그 요청을 +4.5초에 전송했으니 +4.5초에 확보됐다고 볼 수도 없다.

후속 검증에서는 동일 주문의 구간별 상태·여정·등급·승객 일치, 결제/발권 기한, 이후 정상 읽기에서의 유지 여부를 확인해야 한다. 정확한 서버 보유 이벤트 시각이 없으면 “이 응답/조회 시점에는 보유 상태를 확인했다”까지 보고한다. 보유 확인 시점과 실제 보유 시작 시점을 분리한다.

## 5. 시간 예산에 대한 핵심 반려 사유

### 5.1 Date 헤더는 재고 확인 시각이 아니다 — P0

[deadline.py](deadline.py)의 depletion 함수는 Date 헤더 +6초를 P가 +6초까지 존재했다는 근거로 사용한다. 그러나 HTTP Date는 메시지 생성 시각에 관한 정보이며 재고를 읽은 업무 시각이 아니다. 서버가 재고를 먼저 읽고 나중에 응답을 만들 수도 있다. 응답 Date가 09:00:06이라고 해서 그 순간까지 재고가 유지됐다고 증명할 수 없다. HTTP 표준도 메시지 생성 과정 중 Date 값을 만들 수 있다고 설명한다. [RFC 9110 §6.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-6.6.1).

따라서 “마감은 +6초”, “조회가 0.132초 늦었다”는 계산은 설계 근거로 채택할 수 없다. 마지막 P 있음 응답은 안전하게 예약 가능한 마감을 보장하지 않는다. 달력 P는 특정 편명의 확정 재고/좌석 확보와도 동일하지 않다. 원본의 liveOpeningVerified=false도 유지되므로, 개방부터 소멸까지 걸린 시간 자체가 검증되지 않았다.

### 5.2 오프셋 하한을 수신 시각의 상한 계산에 사용했다 — P0

저장된 오프셋 구간은 [2090, 4022]ms인데, 계산기는 낮은 값 2090ms만 전체에 적용한다. 서버 축 경과시간이 `로컬 사건 시각 + 오프셋 − 기준시각`이라면 낮은 오프셋은 이른 경과시간을 만든다. 그것을 없음 응답의 보수적 상한으로 쓸 수 없다.

읽기 전용 재계산으로 동일 depletion 함수에 2090ms를 주면 [6.0, 7.168], 4022ms를 주면 [6.0, 9.1]이 나온 것을 확인했다. **이는 9.1초가 올바른 실제 매진 시각이라는 뜻이 아니라, 기존 7.168초를 입증된 상한이라고 할 수 없다는 반증이다.** Date와 재고 시각을 동일시하는 앞의 오류는 별도로 남는다.

Date 헤더 시계와 브라우저 시계 사이의 불일치 증거는 있다. 다만 원인, 절대 UTC 보정, 서버별 시계 일치, 세션 전체에서 고정 오프셋이 성립하는지는 추가 전제다. 이전 답변의 “시계 결함 확정”과 정확한 선발사 손실 단정도 과도했다. 사용자의 시계 수정 보류 결정은 그대로 존중한다. 이 항목은 운영 시계를 고치자는 요구가 아니라 성능 주장에 사용된 계산의 검토다.

### 5.3 4.506초는 API 실측도 이론적 하한도 아니다 — P0

계산기는 09시 조회 왕복 2.1331초에, 그 실행에서 관측하지 못한 운임 왕복 대신 **달력 왕복 2.3732초**를 더했다. 승객 요청 왕복도 같은 값으로 대체했다. 다른 API의 왕복을 대신 넣는 것은 조건부 산술일 뿐이다. 오늘 실제 일반석 승객 왕복 6.219초와도 크게 다르다.

같은 날 일반석 원본에서 직접 확인한 값은 아래와 같다. 해당 실행은 이미 열린 날짜의 Mac 리허설이며 09시 프레스티지와 다르다.

| 요청 | 요청 시작→본문 완료 |
|---|---:|
| awardAvailability | 1.749초 |
| fareInformation | 1.397초 |
| validateMember | 1.032초 |
| inputTravellers | 6.219초 |

조회+운임만 더하면 3.146초다. 운임 응답에서 inputTravellers 시작까지 실제 간격은 약 5.920초였으며 필수 검증과 화면 대기가 섞여 있다. 3.146초도 다른 대기를 제거했다는 가정의 합계일 뿐 실제 API 실행 결과가 아니다. 이 자료는 왕복이 항상 2초씩 고정되는 것도, 4.5초가 바닥인 것도 아님을 보여준다.

후보 전송 시간은 다음처럼 분해해 평가해야 한다.

`조회 시작 지연 + 조회 왕복 + 선택/검증/구성 비용 + 운임 왕복 + 남은 필수 검증 대기 + 주문 구성/전송 비용`

좌석 보유는 여기에 서버까지의 전달과 보유 처리 시점이 더 관여한다. 확인 응답 완료와도 분리해야 한다. “4.5초 전송이 가능하면 5초 내 확보 가능” 또는 “운임을 생략하지 않으면 3초 불가능”은 현재 자료로 성립하지 않는다.

### 5.4 분석기의 통과 판정은 성능 증거로 사용할 수 없다 — P1

코드 검토상 추가 문제:

- `forecast`는 후보의 전송 시각을 deadline과 비교해 within을 반환한다. 서버 도착·보유 시각은 측정하지 않는다.
- `evaluate`는 관측자와 예매의 노선·날짜·등급·개방 기준 일치를 검증하지 않고 두 폴더를 결합한다.
- 오프셋이 usable=false여도 로컬 NTP 값으로 depletion을 계속 계산하므로 “서버 축 검증 실패”가 마감 생성 중단으로 이어지지 않는다.
- `roundtrips`는 requestStart를 사용하지 않아 실제 전송 시작과 요청 시작이 섞이고, HTTP/업무 성공을 확인하지 않은 표본도 왕복 대체값에 들어갈 수 있다.
- 여러 재고 재등장/소멸 전이를 분리하지 않고 전체의 마지막 있음과 첫 없음을 선택한다.

기존 유닛 시험 통과는 위 업무 가정과 통계적 유효성을 입증하지 않는다. 지금의 budget.json은 검증된 시간 예산으로 사용하면 안 된다. 코드 수정은 이번 범위에 포함하지 않았다.

정적 API가 빠르다는 이유로 회선을 배제하고 서버 부하로 확정한 기존 문장도 근거가 부족하다. 서버 처리 차이, 캐시, 경로 등 여러 원인이 가능하며 지연 원인은 미확정으로 남겨야 한다. “요소 없음” 역시 전부 순수 렌더링 시간으로 분류할 수 없다.

## 6. 치명적 실패 가능성과 누락된 검증

“주문 요청 실행당 1회”만으로 중복 방지가 완성되지는 않는다. 클라이언트가 응답을 못 받아도 서버에서 처리됐을 수 있고, 재실행은 새로운 실행 ID를 가진다. 이 상태에서는 API와 UI 어느 쪽에서도 새 주문을 보내지 않고 먼저 기존 주문을 확인해야 한다. 한 번 전송했다는 로그와 서버 주문이 정확히 한 건이라는 증거는 다르다.

## 7. 검증 순서에 대한 권고

기존 단계별 추진 방향은 유지하되, 구체 요청 필드를 추정으로 확정하기 전에 아래 증거가 필요하다. 이 표는 검토 권고이며 이번에 실행한 작업이 아니다.

1. **오프라인 준비:** 상태 전이, 입력/응답 검증 항목, 불명확 응답·인계 실패·복구 조건을 정의한다. 실제 필드나 “정확히 3회”를 아직 고정하지 않는다.
2. **정상 계약 수집:** 연구 프로필에서 이전 주문 상태를 먼저 확인한다. 주문 전 구간은 새 주문 없이 관측할 수 있다. 주문 생성부터 후반까지의 새 전체 증거는 통제된 일반석 주문 또는 계속 가능한 기존 주문의 정상 경로가 필요하다. 기존 주문만으로 원래 생성 순간을 소급 관측할 수는 없다.
3. **조회·운임 동등성:** 같은 세션에서 정상 UI와 API의 목표·최신 식별자·운임·토큰 변화를 비교한다. 잘못된 노선/날짜/등급, 만료, 업무 오류를 중단하는지 확인한다.
4. **주문과 인계의 조기 검증:** 필수 검증과 선택 문맥을 입증한 뒤 일반석 주문 1회 및 같은 주문 인계를 검증한다. 정확한 좌석 보유 시각이 끝내 확인되지 않더라도 보유 상태 확인과 전송 대리 지표를 분리해 다음 판단에 사용한다.
5. **실제 연결 성능:** Windows에서 후보 전송·응답·보유 확인·인계·실제 결제창을 분리 계측한다. 순차 시험 전 이전 주문 상태를 확인하고 실패도 포함한다. 평균뿐 아니라 각 실행·최대 지연·인계 실패를 보고한다.
6. **실전 적용 판단:** 정상 로그인·검증·현재 주문 유지·기한·목표 결제창을 모두 확인한 뒤 판단한다. 일반석 2회 성공은 기능 증거이며 신규 개방 프레스티지 성공 보장이 아니다.

외부 검토 요청서의 B단계는 “주문 없음”으로 “정상 전체 흐름과 가정 A~D 판정”을 요구한다. 이는 완료 조건이 양립하지 않는다. 수집기가 수동 관측만 한다는 것과 관측 대상 UI가 주문을 만들지 않는다는 것은 다르다. 주문 전 계약 확인과 주문 후 상태/인계를 별도 시험으로 구분해야 한다.

## 8. 권고 결론과 변경 범위

**현재 구조는 폐기할 이유가 없지만, 입증되지 않은 좌석 확보 경계와 6초 마감을 전제로 개발을 고정하면 안 된다.** 핵심은 필요한 정상 상태 전이를 API로 연결하고, 같은 주문을 안정적으로 이어가는 것이다. API 3회·인계 후 추가 조회 0회라는 형식보다 정확한 주문·좌석 상태와 실제 소요시간이 우선이다.

초기 후반 UI 유지안은 합리적인 후보다. 다만 보유가 확인되지 않거나 후반이 재고 확보를 결정한다면 API 처리 경계를 뒤로 옮길 필요가 있다. 반대로 정상 주문 읽기 경로로 인계할 수 있다면 일부 추가 왕복이 있어도 더 안정적인 선택일 수 있다. 이는 계약 수집 결과로 결정해야 한다.

사용자가 요구한 “5초보다 타이트하게”는 개발 목표로 유지할 수 있다. 다만 측정값 없는 확보 보장이나 4.5초 하한으로 바꾸지 않는다. 당장은 **후보 전송 시간 단축 + 보유 상태/기한 확인 + 동일 주문의 실제 결제창 도착**을 별도 통과 기준으로 삼는 것이 적합하다.

이번 작업은 이 보고서 추가뿐이다. 기존 NOW/FACTS/API README 및 검토 요청서의 잘못된 확정 표현은 이 보고서에서 지적했으며 원문을 수정하지 않았다. 구현·운영 시계 수정·실사이트 주문 시험은 수행하지 않았다. 문서와 코드 대조, 로컬 로그 재계산, HTTP Date 표준 확인으로 검토했다.
